## 1. 背景与目标

### 1.1 用户诉求

设置界面模型配置页中，模型下方的参数配置**不能针对某一个模型单独配置**：每个模型的最大上下文等参数可能不一样，目前实现"不够好且界面简陋"，要求**对添加的每个模型都可以单独配置相关参数**。

### 1.2 痛点证据（file:line 均已核实）

| # | 痛点 | 证据 |
|---|------|------|
| 1 | 生成参数是 **profile 级单值**，5 个模型共享一份 temperature/maxOutputTokens/numCtx/reasoningEffort/contextLength | `main.cpp:141-153` profileConfigOf 从 profile 顶层读 4 参数；contextLength 见 `SettingsService.cpp:2252-2273` |
| 2 | **切模型参数不跟随**：聊天区切模型只覆盖 `model` 与 `reasoningEffort`，其余参数沿用 profile 级旧值 | `AgentViewModel.cpp:1054-1055`（仅两键覆盖）；`SettingsService.cpp:1125-1153` selectModelForProfile 同样只改 model/models |
| 3 | 能力表仅 17 条（5 协议），用户手填模型（glm-4 等）查不到，上下文预算落到全局 contextTokens | `LlmProtocolRegistry.cpp:17-78`；解析链 `SettingsService.cpp:2264-2269` |
| 4 | UI 参数卡与模型**无任何关联**，平铺展示，用户无法表达"这个模型用不同参数" | `ModelConfigPage.qml:939-988`（生成参数卡）、`:991-1035`（思考与上下文卡） |
| 5 | updateProfile 通用合并**无 clamp 无校验**透传所有键 | `SettingsService.cpp:970`（`p[it.key()] = it.value()`） |

### 1.3 设计目标

1. **per-model 参数覆盖**：profile 内每个模型可独立覆盖 temperature / maxOutputTokens / numCtx / reasoningEffort / contextLength 任意子集。
2. **切换即跟随**：聊天区切换模型后，本次请求实际使用该模型的生效参数（含上下文预算，衔接 docs/15 已落地的压缩/恢复链路）。
3. **向后兼容零损失**：老 profile 不迁移数据、行为完全不变；profile 级参数降级为"默认值层"。
4. **UI 心智模型清晰**："默认（所有模型）+ 单模型覆盖"两层结构，覆盖状态可见（徽章计数）。

### 1.4 非目标

- 不修改各 LLM Service 请求体结构与 applyProfileParams 逻辑（`main.cpp:139-140` 注释：装配层不按协议分支）。
- 不改 AIAgent 压缩/恢复算法（`AIAgent.cpp:1868-1886` onContextLimitChanged 链路已通，per-model 化只需改传入值的解析）。
- 不做能力表自动发现（API 拉取模型窗口，留作后续增强）。

## 2. 现状分析

### 2.1 数据层

**结论：参数全部落在 profile 顶层键，`models` 是纯字符串列表，两者无结构关联——这是"无法按模型配置"的根因。**

- profile 存储为 QSettings 键 `modelProfiles` 下的 JSON blob（`SettingsService.cpp:39`），schema `kSchemaVersion = 5`（`SettingsSchema.h:17`），apiKey 在 blob 内 DPAPI 加密（`SettingsService.cpp:341`）。
- `models` 为 QStringList；`temperature` / `maxOutputTokens` / `numCtx` / `reasoningEffort` / `contextLength` 均为 profile 级键，经 updateProfile 通用合并透传入库（`SettingsService.cpp:970`），无白名单、无 clamp。
- schema 迁移机制现成：`storedVersion < N` 时调用具名函数（`<2`/`<4`/`<5` 范式，`SettingsService.cpp:317-332`），加 v6 分支即可。
- duplicateProfile 除 apiKey 外全字段深拷贝（`SettingsService.cpp:1058-1091`）。
- removeModelFromProfile 删当前模型时切 `models.first()`（`SettingsService.cpp:1201-1204`）。

## 3. 方案对比与选型

### 3.1 三方案对比

| 维度 | 方案 A：models 升级为对象数组 | **方案 B：新增 modelParams 独立 map（推荐）** | 方案 C：每模型一条 profile |
|------|------|------|------|
| 数据结构 | `models: [{name, temperature, ...}]` | `models: [str]` 不动 + `modelParams: {模型名: {参数}}` | 每模型复制整条 profile |
| models 语义 | **破坏**（UI 芯片/测试断言/ModelSelector 全部要改） | **保持**（纯增量） | 大量冗余 profile（baseUrl/apiKey 重复） |
| updateProfile 合并 | 需改合并+防呆（数组元素结构校验） | **通用合并天然透传新键，零改动**（:970 已透传任意键） | 不涉及 |
| 迁移成本 | 高（models 结构整体迁移，回滚难） | **低**（不搬数据，老 profile 行为不变） | 高（拆分+合并双向迁移） |
| 聊天区切模型 | 中（改 selectModelForProfile 结构读写） | **低**（selectModelForProfile :1135-1140 不动） | 高（切模型=切 profile，波及全部 profile 遍历逻辑） |
| 覆盖子集表达 | 每模型必须全量字段 | **天然支持任意子集覆盖**（缺键=跟随默认） | 天然全量，但浪费 |
| 与能力表/contextLength 三级链衔接 | 需同步改 resolveContextLimitForProfile 数据源 | **只需插入一级"模型覆盖"** | 需按 profile 维度重排优先级 |
| 备份白名单 | 需改 models 结构序列化 | **加 1 键 modelParams** | profiles 数组条目暴增 |
| 爆炸半径 | 大 | **小且集中（读取点已单点收口）** | 大 |

### 3.2 选型结论

**推荐方案 B**。核心理由：

1. **models 列表语义不变**：UI 芯片（ModelConfigPage 卡片三）、`selectModelForProfile` 的 `models.contains/prepend`（SettingsService.cpp:1136-1140）、测试断言、ModelSelector 全部保住。
2. **updateProfile 通用合并天然透传**：`p[it.key()] = it.value()`（:970）对未知键无白名单，modelParams 作为 QVariantMap 整体提交即落库，合并逻辑零改动（docs/15 §2.5 已验证此扩展模式）。
3. **增量迁移成本最低**：v6 迁移不搬任何数据，老用户行为 100% 不变；方案 A 的结构迁移一旦有 bug 是静默数据损坏。
4. **子集覆盖语义天然**：`modelParams` 缺键即"跟随默认"，与"默认值层"两层心智模型精确对应。

## 4. 数据模型设计

### 4.1 modelParams 结构

profile 新增顶层键 `modelParams`（QVariantMap：模型名 → 参数覆盖表）：

```json
{
  "id": "…", "provider": "openai", "apiProtocol": "openai-chat",
  "baseUrl": "…", "apiKey": "…",
  "model": "glm-4",
  "models": ["glm-4", "glm-4-flash", "gpt-4o"],
  "temperature": 0.7, "maxOutputTokens": 4096,
  "numCtx": "", "reasoningEffort": "high", "contextLength": "",
  "modelParams": {
    "glm-4":       { "temperature": 0.5, "contextLength": 128000 },
    "gpt-4o":      { "maxOutputTokens": 8192 },
    "glm-4-flash": { "reasoningEffort": "low" }
  }
}
```

- 覆盖表内**只存显式设置的键**（任意子集）；缺键 = 跟随 profile 默认。
- 允许的键集合与 profile 级参数一致：`temperature` / `maxOutputTokens` / `numCtx` / `reasoningEffort` / `contextLength`。`modelParams` 本身无键时不发送、不占位。

### 4.2 参数读取优先级链

**生成参数（4 项，profileConfigOf 内实现）**：

```
会话临时覆盖(selectedReasoning) > modelParams[model][key] > profile[key]（默认层） > 服务默认（不发送）
```

**contextLength 特有链（resolveContextLimitForProfile 内实现，现为三级）**：

```
modelParams[model].contextLength > profile.contextLength（默认层） > 能力表 contextWindow > 全局 contextTokens
```

> profile.contextLength 在链中位置不变（仍高于能力表），现有用户行为不变；仅 UI 文案从"手动覆盖"调整为"所有模型默认"。语义降级 = 可被 modelParams 覆盖，链位不动 = 兼容。是否保留该层见 §10 待拍板项②。

**读取实现示意（profileConfigOf 改造，main.cpp:141-153）**：

```cpp
// 会话临时覆盖经独立通道传入（见 §4.3），不在 profile 顶层混写
QVariant effectiveParam(const QVariantMap& profile, const QVariantMap& overrides,
                        const char* key) {
    if (overrides.contains(key)) return overrides.value(key);          // ① 会话临时覆盖
    const QString model = profile.value("model").toString();
    const QVariantMap perModel =
        profile.value("modelParams").toMap().value(model).toMap();
    if (perModel.contains(key)) return perModel.value(key);            // ② 模型覆盖
    return profile.value(key);                                         // ③ profile 默认
}
// contextLength 同理在 resolveContextLimitForProfile 的 Priority 1 之前插入 Priority 0
```

### 4.3 会话临时覆盖通道（关键契约）

**问题**：现状把 selectedReasoning 写入 profile 副本顶层（`AgentViewModel.cpp:1055`）再交给 profileConfigOf。per-model 化后，若 modelParams 中该模型有 reasoningEffort，会**反噬盖掉会话临时覆盖**（顶层键同时承担"默认"与"临时覆盖"两个角色，优先级无法区分）。

**处置**：显式拆通道，推荐签名扩展而非隐式改写数据：

```
m_configureModel: void(AIAgent*, const QVariantMap& profile, const QVariantMap& sessionOverrides)
                  （AgentViewModel.h:931 签名 +1 参数）
AgentViewModel::configureModel 构造 overrides = { reasoningEffort: selectedReasoning }（仅有效时）
main.cpp 装配 lambda（:555-573）透传给 profileConfigOf(profile, overrides)
```

- 显式通道契约清晰，避免"改写 modelParams 副本表达优先级"的隐晦做法；未来扩展会话级临时参数（如临时 temperature）无需再改契约。
- **新 Q_INVOKABLE / 回调签名不得依赖默认参数**（QML 调用经 moc 的默认参数有坑，项目惯例），三处调用点同步更新。
- `selectChatModel` 切换时清空 selectedReasoning（`AgentViewModel.cpp:1089` 现状已如此，优先级①自然失效，模型覆盖②接管）。

### 4.4 与 models 的一致性维护规则

| 操作 | 位置 | modelParams 处置 |
|------|------|------------------|
| addModelToProfile | SettingsService.cpp:1155-1186 | 不动（新模型无条目 = 全跟随默认，合法状态） |
| selectModelForProfile | :1125-1153 | 不动（只切当前模型） |
| **removeModelFromProfile** | :1188-1219 | **同步删除 modelParams[model] 条目**（唯一需联动的方法） |
| duplicateProfile | :1058-1091 | 不动（整 map 深拷贝自然携带） |
| 手动拉取模型列表（fetchModels 后 setModels） | ModelConfigPage 拉取按钮 | 允许产生"孤儿条目"（模型不在 models 但 modelParams 有键）：读取无害（不会被选中）、UI 不展示；**不主动清理**，避免拉取误删用户手填覆盖（风险见 §9-R4） |
| 模型重命名 | 现无此功能 | 不涉及 |

**校验规约**（新增 SettingsService 私有 helper，单一出口）：`sanitizeModelParams(QVariantMap)`——丢弃非 map 的 modelParams、丢弃覆盖表内非法键/非法值类型（数字键须可转正数，reasoningEffort 须为合法档位），调用点：updateProfile 合并后、load 反序列化后（`SettingsService.cpp:338-345` 循环内）。弥补现状 :970 无校验的既有缺口，且 per-model 值由 UI 专用入口提交（见 §6），不再裸透传。

## 5. 迁移设计

### 5.1 schemaVersion 5 → 6

- `SettingsSchema.h:17` `kSchemaVersion = 6`（同步更新 :13-16 版本注释）。
- 迁移分支：`SettingsService.cpp:317-332` 处新增 `if (storedVersion < 6) dropLegacyTopPOnUpgrade();`

### 5.2 迁移函数（伪代码）

```
dropLegacyTopPOnUpgrade():
    遍历 m_profiles（JSON blob 反序列化后的 QVariantList）:
        p = entry.toMap()
        若 p 含 "topP":        // 幽灵键，全仓无读写（SettingsBackup.cpp:129 白名单是唯一引用）
            p.remove("topP")
        // modelParams：不预填、不搬运——老 profile 行为完全不变
        // 防御：若 p 已含 "modelParams" 且非 map（不可能来自 v5，防御损坏数据）
        //       则移除该键
        写回并 persist()
```

- 范式完全对齐既有具名迁移函数（clearProfileModelsOnUpgrade / upgradeContextTokenDefault / enableSubagentByDefaultOnUpgrade，SettingsService.cpp:322-327）。
- 备份白名单同步删 topP、加 modelParams（SettingsBackup.cpp:125-131，见 §7 波及点 6）。

### 5.3 备份兼容影响（如实说明）

`SettingsBackup.cpp:420-421` 恢复侧强校验 `schemaVersion == kSchemaVersion`：

| 方向 | 影响 |
|------|------|
| v6 应用 ← v5 备份 | **恢复被拒**（"设置版本不匹配"） |
| v5 应用 ← v6 备份 | 恢复被拒（现状既有行为，v4→v5 时同样发生） |

- 备选（本次不做）：恢复侧放宽为 `≤` 并对恢复数据跑同款 topP 清理——留作后续独立需求。

## 11. 验收标准（EARS 风格）

| # | 标准 |
|---|------|
| AC-1 | 当 profile 的 modelParams 含当前模型的某参数键时，系统应使用该覆盖值装配请求；当不含时，系统应使用 profile 级值；当两者皆缺时，系统应不发送该参数（SamplingParams 既有语义）。 |
| AC-2 | 当 modelParams[model].contextLength 存在时，系统应以其为上下文预算；否则依次取 profile.contextLength、能力表、全局 contextTokens（testResolveContextLimitPriority 范式扩展为四级）。 |
| AC-3 | 当用户在聊天区切换模型时，系统应在下一次请求前按新模型重新解析参数与上下文预算；当新旧预算不同时，系统应触发 onContextLimitChanged 压缩/恢复（docs/15 已有链路）。 |
| AC-4 | 当会话临时覆盖（selectedReasoning）有效时，系统应使其优先于 modelParams 与 profile 默认；当切换模型时，系统应清空该临时覆盖。 |
| AC-5 | 当用户删除某模型时，系统应同步删除其 modelParams 条目；当用户复制 profile 时，系统应携带全部按模型参数且不携带 apiKey。 |
| AC-6 | 当 v5 配置升级到 v6 时，系统应保持全部现有行为不变（不预填 modelParams、参数继续从 profile 级读取），并应从存量 profile 中移除 topP。 |
| AC-7 | 当用户导出备份时，系统应包含 modelParams 且不包含 topP；当恢复 v5 备份到 v6 应用时，系统应拒绝并提示版本不匹配。 |
| AC-8 | UI：当某模型存在覆盖时，系统应在其 chip 与 ComboBox 条目上显示覆盖计数；当用户清空覆盖输入并提交时，系统应删除该覆盖键并回退默认；每行应常显当前生效值与来源。 |
| AC-9 | 全量 `ctest --test-dir build --output-on-failure -j2` 通过（既有用例零修改零回归 + 新增用例全绿）；`qmllint_gate` Error 0；翻译无 unfinished。 |
