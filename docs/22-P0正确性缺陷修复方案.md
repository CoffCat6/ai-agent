## 2. F1 [Blocker] MCP 工具移除时的 use-after-free

### 2.1 待修复项

`ToolRegistry::takeTool()` 返回的所有权被调用方丢弃，在跑的 MCP 工具调用被析构。涉及：

- `src/core/tools/ToolRegistry.h:22-25`（所有权契约注释）、`ToolRegistry.h:63`（`m_ownedTools` 存储类型）
- `src/core/tools/ToolRegistry.cpp:434-447`（`takeTool` 移出 `unique_ptr` 并 erase）
- `src/viewmodels/McpManager.cpp:62-63`（applyRestoredConfigs）、`:111-113`（disconnected 处理器）、`:213-215`（removeServer）、`:256-258`（setEnabled(false)）——四处调用全部丢弃返回值
- `src/core/agent/AIAgent.cpp:1484`（`find()` 取裸指针）、`:1491`（存入 `m_inFlightTools`）、`:1515-1520`（QtConcurrent lambda 按裸指针捕获）
- `src/core/agent/AIAgent.h:283-287`（`m_inFlightTools` 的"无所有权、永不 delete"声明）

### 2.2 实际问题

所有权契约与调用现实相反。`ToolRegistry.h:22-25` 明确注释：

> removes the tool and transfers ownership to the caller — dynamic MCP tools must **outlive their registry entry** while an in-flight execute() may still be running on a pool thread.

即调用方拿到 `unique_ptr` 后必须持有它，让工具活得比注册表条目久。但 `McpManager` 的四处调用形如：

```cpp
for (const auto& tool : client->tools())
    ToolRegistry::instance().takeTool(
        McpToolAdapter::registryNameFor(client->serverName(), tool.name));   // 返回值直接丢弃
```

`unique_ptr` 临时量在语句结束立即析构工具。与此同时，AIAgent 的派发路径持有的是**裸指针**（`AIAgent.cpp:1484` `ITool* tool = m_toolRegistry->find(call.name)`，`:1491` 存入 `QHash<QString, ITool*> m_inFlightTools`，`AIAgent.h:285` 注释 "No ownership - never delete"），并把同一裸指针捕获进池线程 lambda（`:1515-1520`）执行 `tool->execute(call.arguments, cancelled)`。

**触发条件**：任一标签的 agent 正在池线程执行某个 MCP 工具（`McpToolAdapter::execute`，内含最长 35s 的远程调用），此时用户在工具管理页禁用/删除/断连该 MCP 服务器（或设置恢复路径 `applyRestoredConfigs` 清空重连）。

**后果**：两处 use-after-free——① 池线程正在执行的 `McpToolAdapter::execute()` 踩已析构对象（其成员 `client` 指针随 `McpManager::deleteLater` 一并失效）；② `stop()` 遍历 `m_inFlightTools` 调 `it.value()->cancel(...)`（`AIAgent.cpp:1111-1112`）同样踩悬垂指针。`test_mcp.cpp:326-327` 现有用例只验证了"takeTool 后注册表无悬挂条目"，未覆盖生命周期，因此未拦截。

### 2.3 修复后的改善

- **修复前**：断连/禁用 MCP 服务器 × 在跑工具调用 = 悬垂指针，轻则取消失效、重则进程崩溃（偶现、难复现）。
- **修复后**：工具生命周期从"调用方自觉持有"变为**结构化保证**——只要池线程上还有一次 `execute()` 在跑（lambda 持有 `shared_ptr` 强引用），工具就活着；注册表条目移除与对象析构解耦。`McpManager` 四处调用点**语义恰好变正确**（丢弃返回值 = 仅解除注册），无需改动逻辑。
- **代价（负面）**：每次派发多一次 `shared_ptr` 原子引用计数（纳秒级，相对 35s 的 MCP 调用可忽略）；`takeTool` 签名从 `unique_ptr` 变 `shared_ptr`，三个测试文件的调用点因 `auto` 接收而天然兼容，仅需同步注释与断言。

### 2.4 如何修复

所有权模型从 `unique_ptr` 独占改为 `shared_ptr` 共享（推荐方案）。备选方案见本节末尾。

**① `ToolRegistry.h`**：

```cpp
// Batch 31a 契约注释改写为：
// Removes the tool from the registry. The shared_ptr return lets an
// in-flight execute() on a pool thread keep the tool alive: the dispatcher
// holds its own reference (AIAgent::m_inFlightTools / QtConcurrent capture),
// so discarding the returned value is always safe.
std::shared_ptr<ITool> takeTool(const QString& name);
// 新增：供派发路径取强引用（find() 仍返回裸指针，供只读同步查询）
std::shared_ptr<ITool> findShared(const QString& name);

private:
std::vector<std::shared_ptr<ITool>> m_ownedTools;   // 原 unique_ptr
```

**② `ToolRegistry.cpp`**：`registerTool` 将入参 `unique_ptr` 包装为 `shared_ptr` 入列（`m_tools` 裸指针索引不变）；`takeTool` 从 `m_ownedTools` erase 后直接 `return taken;`（`std::move(*it)` 升格为 `shared_ptr` 拷贝）；`findShared` 按名查 `m_tools` 后用 `dynamic_cast` 不必要——直接维护一个 `QHash<QString, std::shared_ptr<ITool>> m_sharedTools` 索引，或最简单：`findShared` 在 `m_ownedTools` 中按名线性查找（工具总数 ≤ 内建 + 64 个 MCP，量级无关紧要）。`listAll`/`toolNamesForModel` 遍历类型随容器自动适配。

**③ `AIAgent.h:283-287`**：`m_inFlightTools` 类型改为 `QHash<QString, std::shared_ptr<ITool>>`，注释改写为"持有强引用：MCP 服务器断连移除注册表条目后，在跑的执行仍安全"。

**④ `AIAgent.cpp` 派发路径（:1484 起）**：

```cpp
const std::shared_ptr<ITool> tool =
    m_toolRegistry ? m_toolRegistry->findShared(call.name) : nullptr;
// m_inFlightTools.insert(call.id, tool) 不变（存的是 shared_ptr 拷贝）
// QtConcurrent::run([tool, call, projectRoot, cancelled] ...) 不变：
// 按值捕获 shared_ptr 即为池线程侧强引用
```

watcher 回调与 `stop()` 的 `cancel()` 遍历（`:1111`）代码不变。

**⑤ `McpManager.cpp`**：四处调用点语句不变；删除 `:212` 误导性注释（"takeTool first … then drop the client"），改为"移除注册表条目即可——在跑的执行持有 shared_ptr，对象自行延迟析构"。

**⑥ 回归测试（`tests/test_mcp.cpp`）**：

- 改写 `:326-327` 既有用例断言：`takeTool` 后 `find() == nullptr`，且 `taken` 上 `execute()` 仍可正常返回（所有权已转移给调用方）。
- 新增用例 **takeTool 与在跑执行并发**：注册一个 scripted 慢工具（`execute` 内 `QTest::qSleep(200)` 后返回标记结果）→ `QtConcurrent::run` 派发 → 主线程立即 `takeTool` 并丢弃返回值 → 等待完成，断言执行结果正确、无崩溃。修复前该用例为未定义行为（可配合 ASan 复现），修复后稳定通过。
- `test_agent.cpp:247`、`test_settings.cpp:1157` 无需改动（`auto` 接收兼容；丢弃式调用语义变为"仅解除注册"，与测试意图一致）。

**备选方案（不推荐）**：ToolRegistry 内部维护"退役列表"（`takeTool` 把工具移入 `m_retired` 向量，延迟 N 秒或下次注册时统一析构）。diff 更小，但生命周期靠超时启发式（MCP 上限 35s，取 60s 宽限）保证，属"大概率对"；`shared_ptr` 方案让生命周期**构造性正确**，且 `ITool` 无二进制兼容负担（进程内接口），改签名无兼容成本。

> **实施记录（✅ 已实施）**：按推荐方案落地，另有两点超出原方案——
> ① `registerTool` 签名改为接收 `std::shared_ptr<ITool>`（`unique_ptr` 可隐式转换，全部既有 `make_unique` 调用点零改动），而非仅内部包装；② `McpToolAdapter::m_client` 由裸指针改为 `QPointer<McpClient>`，池线程 `execute()` 入口先 `m_client.data()` 取局部裸指针再 `invokeMethod`，把"client 已析构"的触达窗口收窄到 invokeMethod 调用瞬间（残余窄窗口见 §9）。
> 测试：`test_mcp` 新增 `takeToolWhileInFlightKeepsToolAlive`（在跑执行中途 `takeTool` 并丢弃返回值，断言执行结果正确、无崩溃），既有 ownership 用例补 `taken->definition()` 可用性断言。

## 3. F2 [Major] 每关一个标签泄漏一个 SQLite 连接

### 3.1 待修复项

per-tab `SqliteMemory` 创建后无人持有、无人释放。涉及：

- `src/main.cpp:422`（`tabAgent->setMemory(new SqliteMemory())`）
- `src/core/agent/AIAgent.h:324`（`IMemory* m_memory{nullptr}`，无所有权语义）、`AIAgent.cpp:143`（`~AIAgent() = default`）
- `src/main.cpp:433-439`（`destroyed` 清理钩子只清 `tabProviderSets / tabMemories / summaryProviders` 三张表，不清 memory）
- 对照：`src/core/memory/SqliteMemory.cpp:85-93` 析构中实现的 `close → removeDatabase`（MEM-702 修复）对 tab 实例永不执行

### 3.2 实际问题

标签工厂里 `new SqliteMemory()` 后立即把裸指针交给 `tabAgent->setMemory()`。`AIAgent` 不拥有它（全工程对该实例无任何 `delete`/智能指针），主 agent 用的是进程级 memory（`main.cpp:324`，见 §3.4 备选方案说明）。因此**每关闭一个标签**：一个 `SqliteMemory` 对象 + 一条以 UUID 命名的活跃 `QSqlDatabase` 连接 + SQLite 文件句柄全部滞留到进程退出。多开多关标签会累积句柄；`SqliteMemory.cpp:85-93` 精心实现的清理路径（先 drop handle 再 `removeDatabase`，注释记录了旧版连接名泄漏教训）对 tab 实例完全空转。

该实例的另一持有者是子对象 `EpisodicService`（`main.cpp:427-428` `summaries->setMemory(tabAgent->memory())`），但 `EpisodicService` **没有析构函数**（grep 证实仅构造函数），不构成回收时机的障碍。

### 3.3 修复后的改善

- **修复前**：开关 N 个标签泄漏 N 条数据库连接；长时间使用后句柄累积，且违背项目自己定下的"单写者、连接可回收"设计意图。
- **修复后**：标签关闭 → 整个 agent 对象树析构完成 → `SqliteMemory` 析构执行 MEM-702 清理，连接与句柄即时归还；主 agent 的进程级 memory 行为不变。
- **代价（负面）**：队列化删除依赖事件循环——若关标签后应用立刻退出，回收回调可能不执行；此时进程即终、OS 回收句柄，无实害（在 §7 风险表中登记）。

### 3.4 如何修复

推荐方案：**工厂持有、销毁信号延迟回收**——所有权放在创建点（`main.cpp` 工厂 lambda），回收挂在既有的 `destroyed` 钩子上，用 `Qt::QueuedConnection` 保证在整个对象树析构完成后执行：

```cpp
// main.cpp 标签工厂（:420 起）
auto* tabAgent = new AIAgent(&app);
tabAgent->setToolRegistry(&ToolRegistry::instance());
auto* tabMemory = new SqliteMemory();          // ← 指针先落名
tabAgent->setMemory(tabMemory);
...
QObject::connect(tabAgent, &QObject::destroyed, &app,
    [tabProviderSets, tabMemories, summaryProviders, tabAgent, tabMemory]() {
        tabProviderSets->remove(tabAgent);
        tabMemories->remove(tabAgent);
        summaryProviders->remove(tabAgent);
        delete tabMemory;                       // ← 新增
    }, Qt::QueuedConnection);                   // ← 新增连接类型
```

`QueuedConnection` 的理由：`destroyed()` 发自 `~QObject` 内部，与子对象（`EpisodicService`，其 `m_memory` 指向同一实例）的析构先后属实现细节；队列化把 `delete` 推迟到事件循环下一次派发，届时 tabAgent 及全部子对象必然已析构完毕，不依赖任何析构顺序假设。

**备选方案（不推荐）**：给 `AIAgent` 增加 `setOwnedMemory(std::unique_ptr<IMemory>)`。被否原因：主 agent 的 memory 是进程级共享实例（`main.cpp:324-328` 同时喂给 `episodicService` 与 `agentVM->setMemory`），一个类里并存"拥有/不拥有"两种 setMemory 语义必然埋下误用；且 `~AIAgent` 体先于 `~QObject` 的子对象析构执行，所有权删除顺序仍需论证。工厂侧回收把所有权留在唯一知道生命周期的地方。

> **实施记录（✅ 已实施，方案微调）**：最终采用了上文的"备选方案"——`AIAgent::setOwnedMemory(std::unique_ptr<IMemory>)` + `m_ownedMemory` 成员，`main.cpp` 工厂改为一行 `setOwnedMemory(std::make_unique<SqliteMemory>())`。推翻原否决理由的依据：
> ① **可测试性**——原方案的回收机制在 main.cpp 组合根 lambda 里，`test_viewmodel` 无法触达；方案自身要求回归测试，机制必须落在可测代码里；
> ② **析构顺序**——`~AIAgent` 体先 detach（`m_episodicService->setMemory(nullptr)`，EpisodicService 无析构函数、该调用使其显式安全），再 `m_ownedMemory.reset()`，全程确定，不依赖 `destroyed()` 信号与子对象析构的先后假设；
> ③ 命名区分（`setMemory` 不拥有 / `setOwnedMemory` 拥有）+ 双方法注释，缓解"双语义误用"。
> 测试：`test_viewmodel` 新增 `ownedMemoryReleasedWithAgent`（直连机制：栈上 agent 析构后 `QSqlDatabase::connectionNames()` 回落基线；端到端：工厂 + `openTab`/`closeTab` 全流程）。

**回归测试（`tests/test_viewmodel.cpp`，扩展现有多标签用例）**：

```cpp
const int baseline = QSqlDatabase::connectionNames().size();
// 循环 3 次：openTab → 发一条消息（可选）→ closeTab，逐轮处理事件循环
QCOMPARE(QSqlDatabase::connectionNames().size(), baseline);
```

连接名为每实例 UUID（`SqliteMemory.cpp` 构造），`connectionNames()` 可直接计数。修复前每轮 +1 不回落，修复后回到基线。

## 4. F3 [Major] 搜索后端 / 嵌入客户端换配置的数据竞争

### 4.1 待修复项

GUI 线程写配置成员、池线程读同一成员，无任何同步。涉及：

- `src/core/tools/WebSearchTool.h:56-63`（`setApiKey/setBackend/setTimeoutMs`，其中 `setBackend` 对 `std::unique_ptr<WebSearchBackend>` 赋值/析构旧对象）；`:74、79、91、100、131`（`execute()` 在池线程解引用 `m_backend`、读 `m_apiKey/m_timeoutMs`）。写方：`src/main.cpp:579-580`（设置回调）。
- `src/infrastructure/embed/OllamaEmbedding.h:16-19`（`setBaseUrl/setModel`）、`:43-44`（成员）；读方 `OllamaEmbedding.cpp` 的 `embed()`（同步单条）与 `embedBatch()`（分页批量，文档导入/RAG 检索在 QtConcurrent worker 上运行）。写方：`src/main.cpp:249-252`（启动装配）、`:640、663`（设置变更回调）。

### 4.2 实际问题

**WebSearchTool**：`web_search` 是 `RequiresConfirm` 工具，确认后在池线程执行 `execute()`，全程解引用 `m_backend->search(...)`（`:91`，内含最长 30s 网络请求）。期间用户在设置页切换搜索后端（Tavily → SearXNG 等）触发 `m_backend = std::move(backend)`（`unique_ptr` 赋值**立即析构旧 backend**）→ 正在 `search()` 中的对象被析构，use-after-free。`m_apiKey`（QString）与 `m_timeoutMs`（int）的跨线程读写同样是未定义行为。

**OllamaEmbedding**：RAG 导入与检索在 QtConcurrent worker 上调 `embed/embedBatch`，读取 `m_model/m_baseUrl` 构造请求 URL；同一时刻用户在设置页改嵌入模型/端点触发 `setModel/setBaseUrl` 对 QString 的无锁写。QString 隐式共享的引用计数并发增减本身就是 UB，最坏崩溃、最坏读出撕裂字符串拼出错误 URL。

**当前侥幸不崩的原因**：写窗口极窄（用户改设置 vs 一次在跑调用重叠是低概率事件）——这正是竞态类缺陷"偶现、难复现"的典型形态。

### 4.3 修复后的改善

- **修复前**：换后端/换密钥/换嵌入模型恰逢在跑调用 = UAF 或 UB（偶现崩溃）。
- **修复后**：在跑调用持快照配置**完整跑完**（结果属于旧配置），下一次调用用新配置——与项目既有产品语义「模型配置更新：运行任务保持原配置，下一轮使用最新配置」（docs/21）完全一致。旧 backend/旧配置对象在最后一次引用释放后自动析构。
- **代价（负面）**：每次调用入口多一次互斥锁（纳秒级）；无语义变化。

### 4.4 如何修复

推荐方案：**配置快照（copy-under-mutex）**——两处同一模式。不推荐"全程持锁"（会把 30s 网络 IO 关进临界区，堵死设置线程）；不推荐"改用信号队列切线程"（过度设计）。

**① `WebSearchTool.h`**：

```cpp
private:
    struct Config {
        std::shared_ptr<WebSearchBackend> backend;
        QString apiKey;
        int timeoutMs;
    };
    // 池线程 execute() 与 GUI 线程 setter 的唯一同步点
    Config snapshot() const {
        std::lock_guard lock(m_configMutex);
        return {m_backend, m_apiKey, m_timeoutMs};
    }

    mutable std::mutex m_configMutex;
    std::shared_ptr<WebSearchBackend> m_backend;   // 原 unique_ptr
    QString m_apiKey;
    int m_timeoutMs{30000};
    std::atomic<bool> m_cancelRequested{false};

public:
    void setApiKey(const QString& key) {
        std::lock_guard lock(m_configMutex); m_apiKey = key;
    }
    void setBackend(std::unique_ptr<WebSearchBackend> backend) {
        if (!backend) return;
        std::lock_guard lock(m_configMutex); m_backend = std::move(backend);
    }
    void setTimeoutMs(int ms) {
        std::lock_guard lock(m_configMutex); m_timeoutMs = qBound(5000, ms, 60000);
    }
```

`execute()` 入口取一次 `const Config cfg = snapshot();`，此后 `m_backend->` 全部改为 `cfg.backend->`、`m_apiKey` 改 `cfg.apiKey`、`m_timeoutMs` 改 `cfg.timeoutMs`（含 `:74` requiresApiKey、`:79` notReadyReason、`:91` search、`:100` 失败提示分支、`:131` providerKey 共五处引用点）。旧 backend 在在跑 execute 的局部 `cfg` 离开作用域后析构。构造函数初始化 `m_backend` 无竞争（对象未发布前）。

## 5. F4 [Medium] 沙箱写路径 junction 穿透

### 5.1 待修复项

`cleanPath` 对不存在的目标不做符号链接解析，写路径校验与实际写入目标可能不一致。涉及：

- `src/core/tools/Sandbox.h:292-298`（`cleanPath`：`canonicalFilePath()` 为空时回退 `absoluteFilePath()`）
- `Sandbox.h:127-131`（`validatePath` 以 `cleanPath` 结果做全部四层判定）
- 影响工具：`write_file` / `edit_file` 新建文件路径（`ToolRegistry.cpp:103`、`:155` 起），以及 `shell_exec` 等一切经 `validatePath` 的写判定

### 5.2 实际问题

```cpp
// Sandbox.h:292-298（现状）
static QString cleanPath(const QString& path) {
    const QFileInfo info(path);
    const QString canonical = info.canonicalFilePath();
    return QDir::toNativeSeparators(canonical.isEmpty()
        ? info.absoluteFilePath() : canonical);   // ← 不存在目标：仅词法折叠 ../
}
```

写路径的常态是**目标尚不存在**（新建文件），`canonicalFilePath()` 返回空，回退的 `absoluteFilePath()` 只做词法折叠，**不解析父目录链上的 junction/symlink**。读路径因目标已存在走 canonical 分支，不受影响。

**攻击面**：项目目录内预植入目录联接 `link` → `C:\Users\<u>\.ssh`（创建 junction 无需管理员权限；植入途径为社工/被导入的恶意项目文件）。模型随后调用 `write_file` 写 `<项目>\link\authorized_keys`——确认对话框向用户展示的是**项目内相对外观路径**，用户误放行后 `validatePath` 按联接路径文本判定"在项目目录内"→ 放行 → `QFile` 沿联接写穿到 `.ssh` 真实目标。同类可指向浏览器配置目录、`C:\Windows` 之外任意黑名单未覆盖的敏感位置。

**风险受控因素**（为什么是 Medium 而非 High）：写入默认限用户目录且项目写入默认关闭（docs/17 P1-4）；需要攻击者先在项目内落一个 junction。但它违反沙箱核心不变量——**"校验通过的路径 == 实际写入的路径"**，且读路径已正确处理（对比之下写路径是明确的能力缺口而非设计取舍）。

### 5.3 修复后的改善

- **修复前**：写目标父链上的 junction/symlink 在创建前不可见，沙箱按文本路径放行，实际写入落点在允许层之外。
- **修复后**：不存在目标会解析"最深存在祖先"的真实落点再拼接尾段——父链上有联接时校验看到的是**穿透后的真实路径**，指向允许层之外的写入被拒绝并返回 `DenyReason`（提示文案随拒绝层级走既有 A5 机制）；读路径行为不变；正常项目内新建文件的放行不受影响。
- **代价（负面）**：`cleanPath` 对不存在目标多一次祖先目录 stat（每次写校验微秒级）；极端深层不存在路径的循环最多走到根，可忽略。

### 5.4 如何修复

**① `Sandbox.h::cleanPath` 改为祖先链解析**（junction/symlink 只可能存在于已存在的目录层；不存在的尾段无链接可解析，`..` 已由 `absoluteFilePath` 词法折叠）：

```cpp
static QString cleanPath(const QString& path) {
    const QFileInfo info(path);
    const QString canonical = info.canonicalFilePath();
    if (!canonical.isEmpty())
        return QDir::toNativeSeparators(canonical);

    // 目标尚不存在（写路径常态）：向上找最深的存在祖先做 canonical 解析
    // （junction/symlink 只能在已存在目录层），再把不存在的尾段按词法拼回。
    QDir dir(QDir::cleanPath(info.absoluteFilePath()));
    QStringList tail;
    while (!dir.isRoot()) {
        const QString parentPath =
            QDir::cleanPath(dir.absoluteFilePath(QStringLiteral("..")));
        const QString parentCanon =
            QFileInfo(parentPath).canonicalFilePath();
        if (!parentCanon.isEmpty()) {
            const QString joined = tail.isEmpty()
                ? parentCanon
                : parentCanon + QLatin1Char('/')
                    + tail.join(QLatin1Char('/'));
            return QDir::toNativeSeparators(QDir::cleanPath(joined));
        }
        tail.prepend(dir.dirName());
        dir.setPath(parentPath);
    }
    // 全链（含根）均不可解析：保持原行为
    return QDir::toNativeSeparators(info.absoluteFilePath());
}
```

**② `validatePath` 入口补设备路径拒绝（2 行加固）**：`\\.\` 与 `\\?\` 前缀绕过 Qt 的规范化，canonical/祖先解析均拿不到真实形态，直接拒绝：

```cpp
if (path.startsWith(QStringLiteral("\\\\.\\"))
        || path.startsWith(QStringLiteral("\\\\?\\")))
    return deny(DenyReason::SystemPath);
```

UNC 共享（`\\server\share`）不在本次加固范围：维持现状并在注释中登记。

> **实施记录（✅ 已实施，方案修正）**：实施期探针（junction 测试内直接断言 `QFileInfo` 行为）推翻了本方案 §5.2 的关键假设——**Qt 6.9 的 `QFileInfo::canonicalFilePath()` 在 Windows 上不穿透 NTFS 联接**：对 junction 目录原样返回联接路径本身（预期中"读路径因目标已存在走 canonicalFilePath 已被覆盖"不成立，读路径同样暴露：`validatePath(<联接>\已存在文件)` 会按联接路径文本放行，而 `QFile` 实际读到穿透后的目标）。
> 因此修复升级为：Windows 侧不再依赖 Qt，改用 **`GetFinalPathNameByHandleW`**（能穿透 reparse point）解析最深存在组件——实现落在新增的 `src/core/tools/SandboxWin.cpp`（`sandboxNativeFinalPath`，`CreateFileW(0 访问权 + FILE_FLAG_BACKUP_SEMANTICS)` 打开 + 取最终路径 + 剥 `\\?\` 前缀；独立 TU 避免 `windows.h` 宏污染）；`cleanPath` 的 Windows 分支自顶向下找最深存在组件解析、再把不存在尾段按词法拼回；POSIX 分支保留 Qt `canonicalFilePath` 祖先链方案（Unix 上它能正确解析符号链接）。该实现同时覆盖读路径：联接后面的**已存在文件**也会解析到真实落点并按其判定。`\\.\` / `\\?\` 设备路径前缀仍在 `validatePath` 入口直接拒绝。
> 测试（`test_sandbox`，Windows-only）：`junctionParentChainResolvedForWrites`——项目内 `mklink /J` 联接到 `C:\ProgramData`，断言写穿透被拒（WritePolicy）、联接内缺失子目录的深层写被拒、联接后已存在文件的读被拒、项目内正常写（含多级不存在父目录）不被误拒，0 skipped；`devicePathsAreRejected` 锁定设备路径拒绝。**实施细节**：mklink 两个参数都必须 `QDir::toNativeSeparators`——`QFileInfo::absoluteFilePath()` 返回正斜杠，mklink 会把 `/ProgramData` 解析成开关而报「无效开关」。

**③ 回归测试（`tests/test_sandbox.cpp`，非 Windows 平台 `QSKIP`）**：

1. **负例（本缺陷）**：`QTemporaryDir` 内建 projectRoot，`QProcess` 执行 `cmd /c mklink /J <projectRoot>\link <外部目标目录>`（junction 无需管理员）→ 设 `s_projectDir = projectRoot`、`s_projectWrite = true` → 断言 `validatePath("<projectRoot>\\link\\newfile.txt", true)` 为 **false**。修复前此断言失败（放行），修复后通过——即用例直接锁定缺陷。
2. **正例（防过度拒绝）**：`<projectRoot>\real\newfile.txt`（real 为真实目录）写校验为 true。
3. **深层新建**：`<projectRoot>\a\b\c\new.txt`（a/b/c 均不存在）写校验为 true 且拼接正确。
4. **读路径回归**：对已存在联接目标的读校验仍被拒（既有 canonical 行为不受改动影响）。
