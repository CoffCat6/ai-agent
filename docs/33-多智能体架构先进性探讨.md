# 多智能体架构先进性探讨

定位：docs/32 给出的"只读子代理"是保守起步形态。本文探讨更先进的多智能体方案，评估哪些值得跟进、哪些不适合本项目，给出演进路线。属架构探讨文档，不含实施承诺。

## 1. 主流范式盘点（2025–2026 生产验证过的形态）

### 1.1 Orchestrator–Worker（主从派生）✅ 本项目 P1 已选

主代理把子任务派给并行的子代理，只回收最终报告。Claude Code subagents、Anthropic 多代理研究系统均属此形态。核心价值被普遍验证为**上下文隔离**而非并行加速——每个子代理有独立上下文窗口，主代理上下文不被中间过程污染。代价：Anthropic 自述多代理 token 消耗约为单代理对话的 15 倍，只在"广度优先、并行探索"类任务上收益为正。

### 1.2 Plan-and-Execute（计划-执行分离）

Planner 产出任务 DAG，Executor 逐项执行，Replanner 在失败或新信息时重排。BabyAGI/LangGraph plan-execute 一脉。适合长程任务，但计划维护本身有 token 开销，且计划偏离实际时反而不如让执行者自主。

### 1.3 Supervisor/Swarm（群聊路由 / 角色移交）

OpenAI Swarm→Agents SDK 的 handoff 模式：多个"角色代理"互相移交控制权；AutoGen 群聊：多代理共享一个对话流，由 manager 决定下一个发言者。角色专业化好，但共享上下文随人数平方级膨胀、行为不确定性高，适合开放域客服/娱乐场景，不适合需要可审计的工程工具。

### 1.4 Graph/State-Machine 编排

LangGraph 式显式状态图：节点是 LLM 或普通函数，边是确定性转移条件，支持 checkpoint、human-in-the-loop 中断。工程可控性最强，但把控制流写成图意味着**预先知道流程**——这正是 agent 存在所要回避的场景。对单用户桌面应用属于过度工程。

### 1.5 Blackboard / 共享工作区（黑板模式）

代理之间不传消息，而是读写共享工件（文件、任务板、scratch 区），以"产出物"为协调媒介。Claude Code 内部的 todo 列表 + 文件系统协作即此思路的实践。优点：中介数据天然持久可查、人类可随时介入读改、通信成本与代理数线性相关。**与本项目"本地优先 + 文件工具丰富"的气质最契合。**

### 1.6 Pipeline / Map-Reduce

确定性扇出-汇总，只适合可均匀分解的任务（批量重构、全库扫描）。作为 spawn_agent 的特例自然获得，不需要独立机制。

### 1.7 Generator–Critic（生成-批判 / LLM-as-Judge）

独立批判代理审查产出后要求修订，可多轮辩论。质量提升显著但成本成倍，业界收敛的用法是**单次批判而非多轮辩论**（一次 review 的性价比远高于 debate）。

### 1.8 合同网 / 市场（Contract Net）

经典 AI 的招标-投标分配，现代生产系统罕用，仅存于学术。忽略。

### 1.9 代理间协议（A2A / ACP）

Google 2025 推的 A2A（Agent Card + JSON-RPC 跨应用代理互操作），解决的是**跨厂商/跨应用联邦**。本地单机桌面应用没有对端，现阶段无场景，记录备查即可。

## 2. 评估框架：六个维度

| 维度 | 权重（本项目语境） | 说明 |
| --- | --- | --- |
| 上下文效率 | ★★★★★ | 用户自带 API Key，token 是真金白银；上下文爆炸直接毁掉长任务 |
| 可控/可审计 | ★★★★★ | 桌面工程工具，用户要能看懂"它到底干了什么" |
| 故障隔离 | ★★★★ | 子任务失败不能拖垮主任务 |
| 并行收益 | ★★★ | 有价值但排在上下文隔离之后 |
| 实现成本 | ★★★★ | Qt/C++ 无现成 agent 框架，一切手写，复杂度溢价高 |
| 人类介入点 | ★★★ | 确认流、中断、编辑中间产物 |

## 3. 对本项目的适配结论

| 范式 | 结论 | 理由 |
| --- | --- | --- |
| Orchestrator–Worker | **采纳（P1 基座）** | 并发单位=服务实例的架构天然支持；上下文隔离收益最大 |
| Blackboard 共享工作区 | **采纳，作为第一演进** | 实现极廉价（子代理本来就有文件工具），解决派生模式的最大短板（结果压缩丢失） |
| Plan-and-Execute 轻量版 | **采纳 ✅ E4** | `todo_write` + 任务清单面板（F1）已是计划载体，E4 补齐稳定 id 与 spawn_agent 对齐 |
| Generator–Critic | **采纳 ✅ E3** | 编码场景高价值：提交前由只读 reviewer 子代理审 diff，接 G4 检查点 |
| 角色档案（专业化） | **采纳 ✅ E2** | docs/32 的 `hint` enum 泛化为用户可配角色（系统提示词 + 工具子集），参照 Claude Code 的 `.claude/agents/*.md` |
| Swarm/群聊 | **不采纳** | token 平方膨胀 + 不确定性，与可审计诉求冲突 |
| Graph 引擎 | **不采纳** | 过度工程；用"主循环 + 工具 + 预算"的隐式控制流已覆盖 |
| A2A/联邦 | **不采纳（备查）** | 无对端场景 |
| 递归派生（子生孙） | **维持禁止** | 复杂度与失控风险非当前收益可比 |

## 4. 演进路线（在 docs/32 P1/P2 之上）

**E1 工件化结果（黑板第一步）✅（2026-11-01，随子代理 P2 交付；证据 UI 入口 2026-11-01 补齐）**：子代理运行结束后，完整过程记录（goal + 全部 assistant/tool 消息）自动落盘为证据工件（AppData/subagents/，单文件 256KB 上限，7 天保留期随派生清理），报告头携带路径；主代理需要细节时用 `file_read` 按需读取（AppDataLocation 在沙箱读允许层内）。与原案差异：工件不写项目内 scratch（避免污染用户工作区/git status），改应用数据目录。纯问答轮次（无工具调用）不落盘。实现于 `SubAgentRunner`（`writeEvidenceArtifact`/`pruneEvidenceArtifacts`）。UI 入口：spawn_agent 的 tool_result 节点携带 `evidencePath`（metadata 白名单持久化），ProcessCard 头部渲染「查看证据」芯片 → `AgentVM.openSubagentEvidence()`，路径先经 `SubAgentRunner::isEvidencePath` 校验（必须落在证据根目录内的真实文件）再交给系统默认 .md 处理器，防止伪造路径逃逸。

**E2 角色档案 ✅（2026-11-01）**：`hint` enum 升级为档案机制，预设 `explore` / `research` / `review`，允许用户在设置中自定义（名称 + 系统提示词 + 允许的工具白名单）。实现：核心侧 `SubAgentRole`（`SubAgentRunner.h`），预设内建于 `SubAgentTool::presetRoles()`；用户档案存设置键 `agent/subagentRoles`（JSON 资产，沿用 promptPresets 模式），设置页 AgentBehaviorPage 新增「子代理角色档案」编辑区（卡片式增删改，白名单逗号分隔输入）。`spawn_agent` 的 schema 由 `hint` 参数升级为 `role`（枚举随角色快照动态重建，模型只能选到实际可解析的名字；`hint` 保留为回退）。安全语义：白名单与只读工具目录取交集，陈旧/越界的白名单只会收窄不会扩权；未知角色返回可读失败并附可用清单；与预设同名的自定义档案覆盖预设。测试覆盖：预设提示词注入、schema 枚举、用户档案覆盖与白名单收窄、未知角色失败、解析器容错与去重、设置往返与复位。

**E3 批判环 ✅（2026-11-01）**：`review` 预设档案已随 E2 就位，本步把批判环模式引导落地——`review` 预设锐化为"单次批判"执行端：子代理先自圈改动集（`git_status`/`git_diff`，或主代理在 context 里点名改动文件），产出按严重度排序、带 path:line 的 findings list，改动干净时明说、不硬凑，明确"修复是主代理的职责"；`spawn_agent` 工具描述增加主循环侧引导——完成一批改动后派 review 子代理、逐条核实并自行修复有效项、不与子代理辩论、仅在新的实质改动批次后复审。与 G4 文件检查点的衔接走自然路径：改动集合由 review 子代理用只读 git 工具自查或主代理在 context 传入，无需注入会话状态。实现于 `SubAgentTool`（`presetRoles()` 的 review 档案 + `definition()` 描述），测试 `reviewCriticLoopGuidanceInPresetAndSchema` 锁定两侧文案。

**E4 计划对齐 ✅（2026-11-01）**：todo 项获得稳定 id（`t1..tn`，单调递增不复用），`spawn_agent` 的 `todo_id` 参数显式关联清单项，子代理报告返回后由主代理按报告同步 todo 状态。至此"计划-派发-汇总-记录"闭环，即 Plan-and-Execute 的全部实效，而无需独立 Planner 实例。实现要点：`todo_write` 是全量替换，项身份靠 AIAgent 侧调和（`reconcileTodoIds`，历史落库前执行）——模型显式回传的已知 id 优先（content 变了也算同一项）、content 匹配次之（每轮每 id 消费一次）、新项分配 `t<n>`（计数器取历史最大后缀，会话内永不复用），伪造/陈旧 id 被替换；带 id 的列表回写进工具结果消息，模型下一轮即可引用。`spawn_agent` 增加可选 `todo_id`：报告头回显（`todo: t2`，提醒模型同步状态）+ 审计 detail 落 `subagent_todo`；goal 仍须自包含（子代理看不见主代理的清单）。面板行前缀显示 id 徽标供人工对应。测试：`todoIdsStableAcrossRewrites`（伪造 id 拒绝/显式回传/content 匹配重排保 id/历史带 id）、`spawnAgentTodoIdEchoedInReportAndAudit`（报告头 + 审计归因）。

**E4.1 清单状态维护（2026-11-03）**：真机测试中模型把 todo_write 当一次性计划（只写一次全 `in_progress` 的初版），最终答案说"全部完成"而任务清单面板仍显示未完成。根因不在面板数据链（`todo_write → reconcileTodoIds → todoListChanged → AgentVM → TodoListPanel` 已验证实时），而是**模型从没再调用 todo_write**，系统提示里也没有任何维护要求。修复：

1. `systemPrompt()` 增加任务清单规则；`effectiveSystemPrompt()` 在用户未覆盖提示时追加 `todoStateBlock(m_todoList)`——每轮把 `id [status] content` 注入系统提示，并在每次 `reconcileTodoIds` 后 `rebuildSystemMessage()`。模型不再依赖几轮前的工具结果（会被压缩/注意力稀释）才知道哪些项没做完。用户 override 仍保持"完全接管"（同引用指令语义，不加注入）。
2. `todo_write` 工具描述与工具结果尾注明确"清单是持续维护的，不是一次性计划；开始/完成一项就全量回写，最终答案前对账"。
3. id 计数器 `m_todoIdSeq` 从当前列表拆出：`todo_write []` 清空后再建项也不会复用 `t1`；`resetSession` 归零、`resumeSession` 按已存 id 对齐。
4. TopBar 任务清单入口改为「列表非空即显示」（角标仍只在未完成 > 0 时显示）——此前全部完成后入口消失，与 F1「任务结束后清单保留可回看」冲突。

测试：`todoStateInjectedIntoSystemPromptAndKeptCurrent`（第 2/3 次请求的系统提示分别看到 `t1 [in_progress]` 与 `t1 [completed]`、工具结果含维护提醒）、`todoIdsNotReusedAfterListClear`（清空后新项为 `t2`）、`statusUpdatesRepaintRowsInPlace`（同一行 in_progress → completed 后标记/删除线/计数实时更新）。

**不排期**：Swarm 群聊、图引擎、跨应用联邦、递归派生、多批判者辩论。

## 5. 一条贯穿性判断

多智能体的"先进性"不在代理数量与拓扑花式，而在三点：**上下文工程**（每个代理只见它该见的）、**工件优于消息**（大块数据走文件不走对话流）、**确定性骨架 + 不确定性决策**（控制流代码写死、LLM 只在决策点出手）。本项目的既有架构——工具即边界、trace 全程落库、预算压顶——恰好是这三点的良好载体；docs/32 的保守起步与 E1–E4 的演进不冲突，都是在这条线上加厚。
