# 子智能体功能方案（H7 落地设计）

来源：docs/26 §4 H7（远期项转正）+ 2026-11-01 架构核查（AIAgent 循环、ToolRegistry、LLM 服务集、线程约束均经源码确认）。对应基线：docs/27 §H7「`subagent`/`spawnAgent` 0 命中；AIAgent 仍单循环」。

## 1. 现状与结论

架构核查结论（文件:行号以当前 HEAD 为准）：

- **主循环**：`AIAgent`（`src/core/agent/AIAgent.h:46`）是单实例单会话 ReAct 循环，跑在 GUI 线程；消息历史为内存 `QJsonArray m_messages`，工具经 `processNextToolCall()`（`AIAgent.cpp:1946`）→ `dispatchToolExecution()`（:2101）在 `QtConcurrent::run` 池线程执行，`QFutureWatcher::finished` 回 GUI 线程续循环。
- **并发单位是服务实例**：`LLMServiceBase` 每实例仅一个在途请求上下文（`src/infrastructure/llm/LLMServiceBase.h:139`），共享实例会串台。现成先例是 `main.cpp:564` 的 `setAgentFactory`——每个会话 tab 一套独立 `AIAgent` + `SqliteMemory` + LLM 服务集（`LlmProtocolRegistry::createServiceSet`）。**子智能体直接套用同一工厂模式即可获得并发能力。**
- **工具系统可复用**：`ITool`（`src/core/tools/ITool.h:97`）+ `ToolRegistry` 进程单例；MCP 工具已经由 `McpToolAdapter` 包装成一等公民。新增工具只需实现 `ITool` 子类并 `registerTool()`。子智能体做成一个 `ITool` 后，MCP 工具、禁用层、策略层自动继承，零额外工作。
- **硬约束**：SQLite 只允许 GUI 线程访问（`src/codemap.md:22,92`）；工具执行在池线程——**子智能体在工具线程里不能直接摸 `SqliteMemory`**。
- **权限模型现成**：`ToolLevel`（Safe/RequiresConfirm/Dangerous）+ `readOnly` 标记（`ITool.h:42`）+ 会话级 `PermissionMode`。RequiresConfirm 在子代理里无人可确认，这是"先做只读子代理"的直接依据（与 docs/26 H7 建议一致）。

## 2. 设计原则

1. **只读先行**：子代理仅暴露 `readOnly == true` 且 `ToolLevel::Safe` 的工具（`file_read`、`list_dir`、`glob`、`grep`、`git_status`、`git_diff`、`knowledge_search` 等）；`web_search`/`http_fetch` 虽为 `RequiresConfirm`（主循环逐次确认的隐私语义），但属 GET 只读检索且 `localOnlyMode=false` 即用户的全局出网同意，同样进入子代理工具面（2026-11-01 修正：初版按 Safe 一刀切漏掉了它们）。localOnly 门镜像 `AIAgent::toolAllowedForModel`：`web_search`/`mcp__*` 摘除、`http_fetch` 保留。写操作一律留在主代理串行执行。
2. **实例隔离**：每个子代理拥有独立的 `IAIService`（照抄 `createServiceSet`）、独立内存态消息历史，与主代理零共享。
3. **可追溯**：审计日志记录 `parent_request_id`；trace 节点带子代理命名空间；子代理最终报告作为工具结果进入主循环历史。
4. **失败隔离**：子代理失败/超时/步数耗尽时返回结构化错误文本，不拖垮主任务。
5. **并行有上限**：进程级并发闸（默认 2，可配），超限排队。

## 3. 架构方案

### 3.1 入口：`spawn_agent` 工具

新增 `src/core/tools/SubAgentTool.{h,cpp}`，实现 `ITool`：

- **name**: `spawn_agent`；**level**: Safe（派生本身无副作用；子代理内部工具各按自身级别门控，但只读档全是 Safe）。
- **schema**：`goal`（string，必填，子代理的任务目标）、`context`（string，可选，主代理补充的背景/约束）、`hint`（enum，可选：`explore` / `research`，影响子代理系统提示词）。
- 主代理一轮回多个 `spawn_agent` tool_call 即天然并行；并发闸负责限流。

### 3.2 执行体：`SubAgentRunner`

新增 `src/core/agent/SubAgentRunner.{h,cpp}`，职责是在**工具池线程**驱动一个精简版子代理循环：

- **不实例化完整 `AIAgent`**：AIAgent 与 TraceModel/SqliteMemory/确认流程强耦合且绑定 GUI 线程，整套搬进池线程代价高。Runner 只复用三块现成能力：`IAIService`（独立实例，`createServiceSet` 创建）、`ToolRegistry::findShared()`（只取只读工具）、`applyContextBudget` 的预算思想（简化版：历史超限时裁剪最早的中间轮）。
- **线程模型**：Runner 的循环在池线程内自旋：`chatComplete()` 是异步信号式且其底层 `QNetworkAccessManager` 需要事件循环——在 `execute()` 内跑一个**专属 `QThread` + 该线程事件循环**承载 Runner 的 QObject 与网络层，工具 future 以 `QSemaphore` 等待完成。不使用 GUI 线程嵌套事件循环，避免与主代理循环重入。
- **停止传播**：主代理 `stopTask()` 触发 epoch 变化时，经 `cancellation` 原子标志传入工具 `execute()`，Runner 检查后中止并回 `sealUnansweredToolCalls` 语义兼容的结果。
- **保护机制**（复用 AIAgent 既有语义的简化版）：步数上限（默认 12，独立于主代理 30）、单任务墙钟超时（默认 5 分钟）、重复调用签名检测、LLM 出错即终止并返回错误报告。
- **产出**：子代理最终回答（或错误原因）作为工具结果字符串回灌主循环，建议格式带头部摘要 + 证据列表（`path:line` 引用），并在日志层记录 token 消耗。

### 3.3 消息与持久化

- **不建子会话、不落消息表**：子代理过程性消息只存在于 Runner 内存，任务结束即丢弃；仅持久化三样——审计日志（含 `parent_request_id`、goal、耗时、token 用量）、最终报告（作为主会话的工具消息自然入库）、trace 节点（见 3.4）。理由：SQLite GUI 线程约束 + 子会话会污染会话列表与上下文预算模型。
- token 统计沿用现有 `token_usage` 链路，标 `parent_request_id` 便于区分主/子消耗。

### 3.4 UI 与轨迹（分两步）

- **P1 最小可见**：`spawn_agent` 的调用与结果走现有工具气泡链路，零 UI 改动；结果文本头部自带"子代理报告"标识。
- **P2 进度面板**：Runner 每轮经队列信号回 GUI 线程写 trace 子节点（命名空间 `subagent.<call_id>`），`TraceModel` 增加节点类型，`AgentViewModel` 转发；对话区工具气泡内嵌"子任务进行中/已完成/失败"状态行。参照 `todo_write` → `TodoListPanel.qml` 的现成"agent 状态 → UI"通道。

### 3.5 设置项

登记进 `SettingsDefinition.h` + `SettingsCatalog`（新增设置键的硬性要求，见 docs/26 §7）：

| 键 | 默认 | 说明 |
| --- | --- | --- |
| `agent/subagentEnabled` | `false` | 总开关；关闭时 `spawn_agent` 不注册 |
| `agent/subagentMaxParallel` | `3` | 并发上限（1–8），超限排队。E2 落地后默认从 2 调至 3：三个预设角色同轮并行派发（explore/research/review）是典型场景，2 会让第三个排队空等；子代理只读，3 仍属保守 |
| `agent/subagentMaxSteps` | `12` | 单个子代理步数上限 |
| `agent/subagentTimeoutSec` | `300` | 单个子代理墙钟超时 |

`tools/disabled` 用户禁用层对 `spawn_agent` 自然生效，无需新机制。

P1/P2 实际形态与原案的差异（实施中收敛）：

- **进度面板降为节点标题**：进度不走独立面板/新 trace 节点类型，而是排队回 GUI 线程更新派生调用 tool_call 节点的 title（`spawn_agent · step k/N · detail`）。标题只保留最新进度，状态徽章仍区分成败。通道为 thread_local 钩子（派发 lambda 安装、SubAgentTool 读取），并行 spawn 各在独立池线程互不串扰，避免改动 ITool 接口与 TraceModel/QML。
- **审计归因零表结构变更**：审计行 request_id 本就是主请求 id（parent 归因天然成立），detail 按 mcp__ 先例扩展 JSON `{"output", "subagent_steps", "subagent_tokens"}`；token_usage 不动（子代理消耗经报告头进入审计与用量口径的聚合层，字段级拆分留待真实需求）。
- **P3 原案**（写类子代理）不变；独立进度面板（若有真实需求）并入体验增强批次再议。

## 5. 回归策略

```powershell
cmake --build build
ctest --test-dir build --output-on-failure            # 当前基线 54 用例零新增失败
ctest --test-dir build --output-on-failure -R "qmllint_gate|test_charts_qml"   # P2 必跑
ninja -C build update_translations                    # P2 新增文案后补齐双语
```

- P1 必须附 `test_agent` 自动化用例（不接受手工验证）；LLM 侧用现有测试桩模式。
- Runner 的线程归属用 `QThread::currentThread()` 断言写进用例，防回归。

## 6. 明确不做

- 子代理写文件/执行命令（P3 另议，需确认冒泡方案）。
- 子代理再派生子代理（禁止递归派生，Runner 内不注册 `spawn_agent`）。
- 子会话在会话列表可见/可切换（子代理不是会话，是任务）。
- 多角色编排（Orchestrator/Planner/Reviewer 等，见 docs/1 远期图）：等只读子代理验证成本与收益后再评估。
