# 34-写类子代理方案（P3）

> 前序：docs/32（子智能体 P1/P2）、docs/33（E1–E4 演进）。
> 本文承接 docs/32 §6「子代理写文件/执行命令（P3 另议，需确认冒泡方案）」。
> 状态：设计页（未实施）。

## 1. 目标与非目标

**目标**：把"改代码"这件重活交给子代理承担——探索、定位、起草补丁——但**落盘权与确认权仍在主代理与用户手里**。子代理产出的是**提案（Proposal）**，不是写入。

**非目标**（本阶段明确不做）：

- 子代理直接写文件、直接执行 shell / 跑测试。
- 子代理自动合入、无人确认地改用户工作区。
- 子代理递归派生、多写者并发编辑同一文件。
- 跨仓库或项目根之外的修改。

**为什么不是"直接给子代理写工具"**：`file_write`/`edit_file` 是 `RequiresConfirm` 工具，确认发生在**主代理的 GUI 线程**（`AIAgent::approveToolCall` + `generatePreview`）。子代理跑在池线程、有自己的 `QEventLoop`，若让写工具在子代理里冒泡确认，需要跨线程挂起一个池线程等待 GUI 决策，并且改动要归因到主代理的 trace——这会把 74fb428 修好的中止路径重新引入竞态面。提案模式绕开整条链路。

## 2. 现状基线（可直接复用的事实）

| 机制 | 现状 | P3 如何使用 |
|---|---|---|
| 子代理工具面 | `SubAgentTool::refreshCatalog()` 在 GUI 线程快照 `ToolLevel::Safe && readOnly`，排除 `spawn_agent` | 新工具 `propose_edit` **本身只读**，天然落在同一过滤规则内，安全边界零改动 |
| 主代理写入 | `file_write` / `edit_file` 均 `RequiresConfirm`，`generatePreview()` 产出 diff，`approveToolCall()` 决定是否派发；`AutoEdit` 仅放行 `autoEditSafe` | 提案由主代理用现有写工具应用，确认气泡与 diff 预览**原样复用** |
| 沙箱 | `Sandbox::validatePath(path, isWrite, ...)` + 派发时钉住的 `ExecutionScope(projectRoot)` | 提案的路径校验沿用同一函数，读权限即提案权限 |
| 检查点 | `FileCheckpoint` 支持回滚 | 应用提案后文件改动照常进 checkpoint，无需新机制 |
| 证据工件 | `SubAgentRunner` 把完整 transcript 写入 AppData/subagents/（256KB、7 天） | 提案全文随工件落盘；报告内联摘要 |
| 过程可视化 | 派生节点 `subagentLog`（50 条）+「查看证据」芯片 | 提案计数可作为卡片徽章（P3.2） |

## 3. 核心设计：Proposal-as-tool-result

### 3.1 新工具 `propose_edit`（Safe + readOnly）

子代理唯一的"写"意图出口，但实现**不触碰磁盘**：

```jsonc
{
  "path": "src/core/agent/AIAgent.cpp",      // 相对项目根
  "rationale": "避免标题请求在 episodic 关闭时挂死",  // 一句话理由
  "edits": [                                  // 至少一条
    { "find": "if (!m_enabled) return;", "replace": "if (!m_enabled) { emit ...; return; }" }
  ]
}
```

校验（全部只读，在子代理线程完成）：

1. `Sandbox::validatePath(path, /*isWrite=*/false)` 通过，且必须在项目根内（提案只针对工作区源码）。
2. 文件存在、可读、是普通文本文件（拒绝二进制、拒绝超过 `kProposalMaxFileBytes`）。
3. `find` 在文件当前内容里**恰好出现一次**——0 次或多次都返回可读失败（"ambiguous anchor, add more context"），模型改参数重试；不猜。
4. `edits` 数量 ≤ `kProposalMaxEditsPerCall`（3），单个 `replace` ≤ `kProposalMaxEditBytes`（8 KiB）。
5. 单次运行提案总数 ≤ `kProposalMaxPerRun`（20），超出返回失败并提示收敛。

成功返回（给子代理看的）：`Proposed 2 edit(s) to src/... (not applied). The primary agent will apply them after user approval.` —— 明确告知"没写盘"，避免模型误以为已生效。

> 为什么用 find/replace 而不是 unified diff：模型生成 hunk 行号极易错位；锚点文本 + 恰好一次匹配是**可机械验证**的，错了立刻报错而不是在应用阶段炸。

### 3.2 提案的汇聚与呈现

- `SubAgentRunner` 从 `propose_edit` 的 tool 结果里解析结构化提案，收集进 `SubAgentReport::proposals`（`{path, rationale, edits[]}`）。
- 报告文本追加 `## PROPOSALS` 段：每条给出 path、理由、以及由 find/replace 生成的**展示用 unified diff**（仅用于阅读，应用时不依赖行号）。
- 证据工件（E1）同时包含提案全文——主代理可 `file_read` 细看。
- 派生 trace 节点 metadata 新增 `subagentProposals`：轻量索引 `[{path, rationale, count}]`，随 metadata 白名单持久化；卡片据此显示"N 个改动提案"徽章（P3.2）。**正文不进 metadata**（避免节点膨胀），全文走报告/工件。

### 3.3 主代理应用（复用确认流）

系统提示增补一段引导（写入 `systemPrompt()`）：

- 收到 `## PROPOSALS` 后，**逐条**用 `edit_file`（新文件用 `file_write`）应用，`old_string` 取提案里的 find 原文、参数与提案一致；
- 应用会触发用户确认——**不得**把补丁原样复述给用户当"已完成"；
- 每批应用后自行复核（重读文件 / 跑构建），确认无误再继续；
- 提案与当前文件不一致（锚点失效）时，不要硬套：重读文件、重新定位，必要时再派生一个子代理。

现有确认气泡不需要改动：`edit_file` 的 `generatePreview()` 已经产出 diff，用户点「允许」才落盘。`AutoEdit` 会话模式按既有语义自动放行 `autoEditSafe` 工具——这是用户自己在会话级的选择，不新增权限面。

## 4. 角色档案

新增预设 `coder`（`SubAgentTool::presetRoles()`）：

- **提示词**：先读后改；一次只解决一个可验证的小目标；优先最小改动；每个提案必须给出 rationale；不确定就多读、不要猜；不改与目标无关的代码；不写测试之外的"顺手优化"。
- **工具白名单**：`read_file, list_dir, glob, grep, git_status, git_diff, git_show, propose_edit`。
- 白名单与只读目录取交集（E2 既有语义，陈旧白名单只会收窄）——`propose_edit` 加入只读目录后自动可用。

`explore` / `research` / `review` 三个预设不授予 `propose_edit`：探索者不该起草改动，职责分离也降低误用。

## 5. 安全与边界

- **无新写路径**：`propose_edit` 不碰磁盘；真正的写入只发生在主代理的 `RequiresConfirm` 工具里，权限模型不变。
- **路径收敛**：提案路径必须在项目根内；绝对路径、`..` 逃逸由 `Sandbox::validatePath` 拒绝。
- **锚点歧义即失败**：不做模糊匹配，杜绝"改错位置"。
- **配额防刷**：单次调用 3 条、单次运行 20 条、单条 8 KiB、单文件 1 MiB 上限；超限是可读失败而非截断——截断会产出半个补丁。
- **归因清晰**：提案归属派生节点与证据工件；实际写入的 trace/审计仍记在主代理名下，与用户确认一一对应。
- **失败可见**：子代理以 `Stop::Budget`/`Error` 收场时，已收集的提案照常返回（带 `partial: true` 标记），主代理可选择只应用已验证的部分。

## 6. 测试策略

| 层 | 用例 |
|---|---|
| `propose_edit` 单元（test_agent 内 fake 服务剧本） | 路径逃逸拒绝；二进制/超大文件拒绝；find 0 次/多次拒绝并给出可读原因；超配额拒绝；合法提案返回 success 且**磁盘字节不变** |
| Runner 汇聚 | 两轮共 3 条提案 → `report.proposals` 数量与顺序正确；报告文本含 `## PROPOSALS` 与 diff；`partial` 标记 |
| 主代理闭环 | 子代理产提案 → 主代理剧本调用 `edit_file` → 模拟确认 → 文件内容变化；**未确认时文件不变**（负向用例） |
| 提示词/描述 | `coder` 预设含"先读后改/最小改动/rationale"关键词；`spawn_agent` 描述含提案应用引导（锚点式断言，锁文案） |
| 持久化 | `subagentProposals` metadata 往返（test_memory） |
| UI（P3.2） | 卡片徽章显示提案数；展开可读 `## PROPOSALS` 段 |

不接受手工验证替代自动化；LLM 侧一律用现有 `RecordingFakeService` 剧本桩。

## 7. 分阶段

- **P3.1（核心闭环，无 UI）**：`propose_edit` 工具 + Runner 汇聚 + 报告渲染 + `coder` 预设 + 系统提示引导 + 测试。
- **P3.2（可见性）**：派生节点 `subagentProposals` metadata + 卡片徽章/提案段渲染；翻译双语。
- **P3.3（体验）**：同一文件多提案的合并提示、应用失败时的自动重定位建议。

## 8. 曾考虑且否决的替代方案

1. **虚拟覆盖层文件系统（dry-run overlay）**：子代理正常调用 `edit_file`，写入落到内存 overlay，结束后 diff 回放。否决原因：要为所有写工具做 overlay 感知、沙箱语义变复杂、且模型无法自校验"改完能不能编译"，收益不抵复杂度。
2. **子代理内确认冒泡**：写工具在子代理里挂起并弹主界面确认。否决原因：池线程等待 GUI 决策，打断中止/超时路径（docs/32 §8 的同类竞态），且写入归因会横跨两个 trace。
3. **子代理直接写临时分支 / worktree**：需要 git 分支管理与会话级工作区语义。否决原因：与"单工作区、用户可见即所得"的产品前提冲突，用户还得自己合并。
