# 35-主代理与子代理并行方案

> 前序：docs/32（子智能体 P1/P2）、docs/33（E1–E4）、docs/34（写类子代理 P3）。
> 本文回答两个问题：主代理与子代理当前如何并行？还能在哪些维度完善？
> 状态：P4.1–P4.6 已实施（2026-11-02）。基线盘点：2026-11-02。

## 1. 结论先行

- **执行层已并行，推理层没有。** 子代理跑在 `QtConcurrent` 池线程，多个
  `spawn_agent` 同一轮可并发；但主代理的 LLM 循环停在轮次屏障上，必须等
  本轮**所有**工具（含子代理）返回后才发起下一次请求。主代理不会在子代理
  运行期间"继续思考下一轮"。
- **子代理内部是串行的。** 同一轮的多个工具调用按顺序逐个执行，没有利用
  只读工具之间天然的可并发性。
- **真正的"主/子并行"可行，但必须换协议**：`spawn_agent` 立即返回启动确认
  （ack），新增 `subagent_wait` / `subagent_status` 取回结果。原因见 §2.3：
  OpenAI 的 `tool_calls` ↔ `tool` 配对契约不允许主代理在子代理结果未定时
  继续说下一句。
- **建议顺序**：先做低风险、纯收益的 P4.1（上下文预算）与 P4.2（子代理内部
  并发），再做 P4.5（队列/单任务取消）与 P4.4（提案结构化应用），最后做
  P4.3（后台子代理）——它涉及协议、生命周期与 UI，需要单独一轮设计评审。

## 2. 现状基线

### 2.1 并行矩阵

| 维度 | 当前 | 说明 |
|---|---|---|
| 多个子代理之间 | **并行** | 同一轮多个 `spawn_agent` 一起派发；全局并发闸默认 3（1–8 可配） |
| 主代理同轮的其他工具 | **并行** | 自动放行的工具与子代理一起进 `parallelCalls`，各自 `QtConcurrent::run` |
| 主代理"继续下一轮" | **不并行** | 轮次屏障等所有在飞工具结束；确认态还会暂停整队 |
| 子代理内部多个工具 | **串行** | `SubAgentRunner` 的 `for` 循环逐个 `execute` |
| 子代理再派生子代理 | **禁止** | 目录快照排除 `spawn_agent`（刻意防递归放大） |
| 不同会话（tab） | **并行** | 每个 tab 独立 `AIAgent` 与 LLM 服务；子代理并发闸是全局共享的 |

### 2.2 代码链路

主代理一轮：

```
assistant(tool_calls)
  → processNextToolCall            AIAgent.cpp:2104
      ├─ 未知/禁用/PlanOnly/未自动放行 → 回填错误或挂起确认
      ├─ 自动放行 → parallelCalls  AIAgent.cpp:2218
      └─ dispatchToolExecution     AIAgent.cpp:2252
            → QtConcurrent::run（安装 ExecutionScope + 进度路由）
  → finishToolExecution            AIAgent.cpp:2458
      → if (!m_inFlightTools.isEmpty()) return;   AIAgent.cpp:2581
      → processNextToolCall → processIteration（下一轮 LLM）
```

子代理：

```
spawn_agent
  → SubAgentTool::execute          SubAgentTool.cpp:289
      → acquireSlot（全局闸）      SubAgentTool.cpp:266
      → SubAgentRunner::run        SubAgentTool.cpp:368（同步阻塞）
          → 每轮 chatComplete + 自建 QEventLoop
          → for (call : toolCalls) entry->tool->execute(...)  SubAgentRunner.cpp:517/536
```

### 2.3 三个硬约束

1. **轮次屏障**：`finishToolExecution` 只有在 `m_inFlightTools` 清空后才推进
   下一轮（AIAgent.cpp:2581）。这是消息历史一致性的保证——同一条 assistant
   消息的所有工具结果必须成批回灌。
2. **OpenAI 配对契约**：assistant 的每个 `tool_calls[].id` 必须在**紧接着**
   的 tool 消息里得到结果，之后才能出现下一条 assistant 消息。因此"主代理先
   说一句、子代理结果稍后补上"在原协议下非法；后台化必须让 `spawn_agent`
   的 tool 结果变成一次性 ack，再用新的工具调用去取回结果。
3. **线程局部上下文**：`SubAgentProgressRouter`、`SubAgentProposalSink` 都是
   `QThreadStorage`。子代理的嵌套工具目前在**运行线程**上执行，所以能看见；
   一旦把工具搬到别的线程（P4.2），这两项要么按线程安装，要么排除在该线程
   之外（`propose_edit` 必须留在运行线程）。

## 3. 目标与非目标

**目标**

- 让子代理在长任务下不因上下文溢出而失败（P4.1）。
- 降低子代理单轮多工具串行等待的延迟（P4.2）。
- 提供"启动 → 主代理继续 → 取回"的并行形态，且不破坏工具配对契约（P4.3）。
- 让提案的应用不再依赖模型抄写长报告，减少截断与锚点错误（P4.4）。
- 让排队与取消在 UI/工具层可感知、可精确操作（P4.5）。

**非目标**

- 同一会话并行两条主代理循环（历史会交错，暂不做）。
- 子代理递归派生（深度保持 1；后台任务也不放开）。
- 子代理直接写盘 / 跑命令（docs/34 的提案模式不变）。
- 后台任务跨重启恢复（第一版只做进程内；结果落 trace 即持久化）。

## 4. P4.1 子代理上下文预算

**问题**：主代理有 `applyContextBudget`（AIAgent.cpp:1494），子代理完全没有。
Runner 只做单条工具结果 6000 字符截断；步数无上限后，历史会一直增长，小上下文
模型（32k）在几十轮后就可能 400 或静默截断。

**为什么不能直接复用 `compressToFit`**：`TokenEstimator::compressToFit`
（TokenEstimator.h:99）保留首条 system，然后从某条 **user** 消息起保留最大
后缀。子代理历史只有开头一条 user（goal），之后全是 assistant/tool，函数会
认为"从 goal 起全都保留"，等于不压缩。

**设计**

1. `SubAgentRequest` 增加 `int contextLimit{0}`（0 = 不设限）。`main.cpp` 的
   子代理 profile 快照里补 `settings->resolveContextLimitForProfile(spawnProfile)`
   （与主代理 `setContextLimit` 同源，main.cpp:563）。
2. 新增 `TokenEstimator::compressToolRoundsToFit(messages, maxTokens)`：
   - 恒保留 `messages[0]`（system）与 `messages[1]`（user goal）；
   - 以 "assistant + 其后连续 tool 消息" 为一个不可拆单元，从最旧的轮次开始
     整体丢弃，插入一条 `user` 提示
     `[Earlier tool rounds omitted to fit the context window]`（不写进持久化，
     只存在于本次运行的 messages）；
   - 丢弃后仍超预算时，再对剩余 tool 结果做二次减半截断；
   - 绝不留下孤儿 tool 消息（配对契约）。
3. 每轮 `chatComplete` 前估算
   `estimateTokens(messages) + estimateToolsSchema(tools)`；超限才压缩，并
   通过进度事件 `phase = "context"` 记录 `compressed X → Y messages`，同时
   追加到证据工件（E1）便于事后核对。
4. 单轮失败兜底：若仍因 context length 被服务端拒绝，报告归类 `Stop::Error`
   并在文本里给出"可重新派发、缩小 goal 范围"的建议。

**验收**：设小预算（如 4000）跑 20+ 轮大工具结果，运行完成、无 400；首条
system 与 goal 保留；任意 tool 消息都有前置 assistant 声明；报告 tokens 正常。

**实施记录（2026-11-02）**

- `SubAgentRequest::contextLimit` + `SubAgentTool::setContextLimit()`；
  `main.cpp` 的 profile 快照按 `resolveContextLimitForProfile(spawnProfile)`
  刷新，与主代理同源。0（未知）时行为与之前完全一致。
- `TokenEstimator::compressToolRoundsToFit(messages, maxTokens, *omittedRounds,
  *truncatedResults)`：以「assistant + 其后连续 tool」为不可拆单元整轮丢弃，
  保留 system + goal；插入 `user` 提示（带省略轮数）；仍超预算时对最大的
  tool 结果反复减半（下限 400 字符，带 `[truncated to fit context]` 标记）。
- **只压缩线上副本**：Runner 每轮把 `messages` 复制成 `wireMessages` 再压缩，
  完整转录仍用于下一轮与 E1 证据工件——早期证据不会因压缩而从工件里消失
  （比原设计"压缩事件写进工件"更强的保证）。
- 进度事件 `phase = "context"`（`N earlier round(s) omitted, M tool result(s)
  truncated (X → Y messages)`）经 `AIAgent::applySubAgentProgress` 追加到
  `subagentLog`；ProcessCard 用 `↺` + 次要色渲染。
- 预算口径：`capacity = contextLimit - estimateToolsSchema(wireTools)`；
  forced-final 轮（无工具 schema）容量相应变大。
- 测试：`test_token_estimator` 三个纯函数用例（丢旧轮保配对 / 巨结果截断 /
  未超限不动）；`test_agent::subagentCompressesContextOnTheWire` 用 6 轮
  2400 字符结果 + `contextLimit=1200` 断言：每轮请求保留 header、无孤儿
  tool、不超窗、压缩事件可见、最新请求丢掉最旧轮、证据工件仍含完整转录。

## 5. P4.2 子代理内部工具并发

**问题**：`SubAgentRunner.cpp:517` 的循环串行执行同一轮的所有工具。一个
"5 个 grep + 2 个 read_file"的勘察轮次在子代理里要排队，而主代理的同轮工具
是并发的。

**设计**

- **只并行只读工具**：`entry.def.level == Safe && entry.def.readOnly`，显式
  排除 `propose_edit`（它依赖运行线程的 `SubAgentProposalSink`；提案的生成
  顺序也不应被打乱）。
- 使用 Runner 自有的小型 `QThreadPool`（建议 4 线程），不用全局池：主代理
  并发闸 3 × 子代理内部 3 = 9 个嵌套任务，全部压全局池会和主代理的工具/
  嵌入任务抢线程，出现饥饿。
- 每个调用 `QtConcurrent::run`，全部 future 完成后**按原始顺序**回填 tool
  消息、按原始顺序发进度事件（日志稳定、测试可断言）；并发上限
  `kSubToolParallelCap = 3`，超出的按批执行。
- 取消：派发每个调用前检查共享旗标；在飞工具照常拿 `request.cancelled`，
  `stop()` 依然能整体级联。
- **线程契约**：`request.progress` 必须允许从任意线程调用。真实装配里的
  lambda 只是 `QMetaObject::invokeMethod(..., QueuedConnection)`，满足；
  测试里的假钩子也必须遵守（文档写明，避免将来引入线程不安全的钩子）。
- `propose_edit` 与其他工具混在同一轮时：只读工具并发、`propose_edit` 在
  运行线程串行执行，结果仍按原顺序回填。

**验收**：假工具用 sleep + 并发计数器证明最大并发 > 1 且 ≤ 上限；结果顺序
与调用顺序一致；混合 `propose_edit` 的 coder 运行提案数量/顺序不变；并发
期间 `stop()` 能在一个轮询片内收敛。

**实施记录（2026-11-02）**

- `SubAgentRunner::kSubToolParallelCap = 3`；Runner 每次运行构造自己的
  `QThreadPool`（maxThreadCount = cap），不碰全局池。
- 同一轮按原始顺序扫描：连续的可并行调用（`Safe && readOnly` 且不是
  `propose_edit`）按 cap 切成批次，整批 `QtConcurrent::run` 后统一
  `future.result()`，再**按调用顺序**回填 tool 消息与进度事件；未知工具、
  `propose_edit` 与其他非只读工具仍在运行线程串行执行。混排轮次的 wire
  顺序因此与调用顺序完全一致。
- **线程局部上下文补齐**：`Sandbox::ExecutionScope` 是线程局部的，测试
  暴露出 worker 线程丢失主代理钉住的项目根（相对路径被沙箱拒绝）。Runner
  在运行线程先快照 `Sandbox::currentProjectDir()`，每个 worker lambda 内
  重建 `ExecutionScope`。这是纯函数级并发方案必须补的线程契约。
- 取消：每批派发前检查共享旗标；已在飞的调用照常收到 `request.cancelled`
  并 join，之后报告归类 `Stop::Cancelled`。进度钩子仍只在运行线程调用。
- 测试：`subagentReadOnlyToolsRunConcurrently`（5 个 120ms 睡眠工具：峰值
  2–3、结果 `call_0..4` 按序）；`subagentMixedRoundKeepsCallOrder`
  （`[read_file, propose_edit, read_file]`：wire 顺序不变、提案段正常、
  文件未落盘）。

## 6. P4.3 后台子代理（fork/join）

### 6.1 工具面

- `spawn_agent` 新增可选参数 `background: bool`（**默认 false**，保持现有
  调用与测试语义）。`background=true` 时立即返回：
  `[Sub-agent started] id=sa-3. Collect with subagent_wait(id) when needed.`
  这个 ack 就是该 `tool_call` 的合法 tool 结果，配对契约不破。
- 因为默认值是 false，`spawn_agent` 的描述与系统提示要明确引导：**长耗时、
  与主任务后续步骤无依赖**的勘察/起草任务用 `background=true`；需要结果才能
  继续推理的短任务保持同步。
- 新增两个全局工具（仅在子代理启用时注册，且从子代理目录中排除）：
  - `subagent_wait(id, timeout_ms?)`：阻塞直到完成或超时（超时上限 10 分钟，
    超时返回 success + `state=running`，提示稍后再取，不算失败）；
  - `subagent_status(id)`：非阻塞返回状态、已用步数、进度摘要；
  - （可选）`subagent_cancel(id)`。
- 报告取回后沿用现有逻辑：`ToolResult.metadata` 带提案索引、报告文本带
  `## PROPOSALS`、证据工件照常写入。

### 6.2 生命周期

- 会话级注册表（`AIAgent` 拥有）：`taskId → {state, goal, role, startedAt,
  report, progressTail}`；`SubAgentTool`/Runner 只负责跑，通过回调把状态
  排队回 GUI 线程。
- 状态机：`Queued → Running → Completed | Failed | Cancelled`。
- 上限：每会话 `kMaxBackgroundTasks = 4`；TTL 30 分钟（超时自动取消并留在
  `Failed`，保留原因）。
- **主任务结束时：继续跑**（已定）。结果留在注册表，主任务结束后用户仍可在
  面板里查看；下一轮用户消息里模型可 `subagent_status` 取回。会话关闭或应用
  退出时统一取消。
- 进程内存储，不跨重启；完成时仍写 trace 节点，因此"结果已出"这一事实可
  随会话持久化。

### 6.3 线程与进度

- 后台运行不能复用派发 lambda 的线程局部进度钩子（lambda 在 ack 后立即返回，
  router 随之失效）。改为按 `taskId` 的进度回调：Runner 的 `notify` 直接调用
  一个线程安全的回调，`QMetaObject::invokeMethod` 回 GUI 线程更新任务节点。
- 后台任务在 trace 中拥有独立节点（`type = "subagent_task"`，metadata 带
  `taskId/goal/role/state`），ProcessCard 渲染运行/完成/失败与提案徽章；
  `spawn_agent` 的 ack 节点只负责"已启动"。

### 6.4 为什么不做"完成时注入消息"

把结果作为一条 user/system 消息插进主历史，看似省工具，但会带来：主任务可能
已经结束、消息顺序与请求在飞互相踩、会话恢复时出现"来历不明"的 user 消息、
审计归因断裂。fork/join 把取回时机交给模型显式决定，历史里每一步都有对应的
工具调用，可审计、可恢复。

### 6.5 后台任务面板（已定：独立面板）

后台任务不塞进右栏——它是**会话级**的（本地会话也有），而右栏（ContextPanel）
只服务项目级内容；也不只靠 trace 卡片，否则任务一多就要在长会话里翻找。沿用
TodoDialog 的既有模式：**顶栏入口 + 独立 Dialog**。

**数据通道**

- `AIAgent` 的会话级任务注册表是唯一事实源；状态变化经排队信号回 GUI 线程，
  合并节流（250ms）后发出 `backgroundSubAgentsChanged`。
- `AgentViewModel` 暴露：
  - `Q_PROPERTY(QVariantList backgroundSubAgents ...)` —— 每项
    `{ id, goal, role, state, startedAt, elapsedMs, steps, proposalCount,
       progressTail: [{phase, text}] (最多 3 条), error }`；
  - `Q_PROPERTY(int backgroundSubAgentActiveCount ...)` —— 排队 + 运行中，
    给顶栏角标；
  - `Q_INVOKABLE void cancelBackgroundSubAgent(QString id)` /
    `cancelAllBackgroundSubAgents()`；
  - `Q_INVOKABLE QString backgroundSubAgentReport(QString id)` —— 展开时才取
    全文，列表更新不携带大字符串；
  - `Q_INVOKABLE void dismissFinishedBackgroundSubAgents()`；
  - `Q_INVOKABLE void revealBackgroundSubAgent(QString id)` —— 跳到对应 trace
    节点（可选）。
- 切换会话时直接读该会话的注册表；任务不跨会话串台。

**顶栏入口（TopBar）**

- 与「任务清单 / 审阅 / 过程开关」同排的 IconButton（建议新增一个 `agents`
  图形，暂可复用 `layers`），`visible: activeCount > 0`；
- 角标 = 排队 + 运行中数量；tooltip「后台子代理（N 个进行中）」；
- 点击 `backgroundTasksDialog.open()`。

**Dialog（`BackgroundTasksDialog.qml`）**

- 宿主契约与 TodoDialog 一致：main.qml 声明实例、`parent: Overlay.overlay`、
  数据绑定 `AgentVM.backgroundSubAgents`；
- 头部：标题 + 汇总（`N 个运行中 · M 个排队`）；宽度上限 ~560px；
- 每一行：状态点/徽章（排队/运行/完成/失败/已取消）、角色名、goal（最多两行
  省略）、运行中任务的实时耗时（行内 1s 定时器，不依赖后端刷新）、步数、
  提案数徽章；
- 行操作：
  - 「停止」仅对排队/运行中可见 → `cancelBackgroundSubAgent(id)`；
  - 「查看」展开行内详情：最近 3 条进度 + 完整报告（按需
    `backgroundSubAgentReport(id)`）+ 证据路径入口；
  - 「定位」跳到 spawn 节点（可选）；
- 已结束任务保留在列表，直到用户「清除已结束」或会话关闭；
- 空态：「没有后台任务。模型对长耗时任务使用 background 模式时会出现在这里。」
- 无障碍：列表区 `Accessible.role: List`，每行可读状态与 goal。

**与 trace 的关系**：面板是管理面，trace 是时间线。两者读同一份注册表/节点
数据，不做双向编辑；从面板「定位」只滚动与高亮，不改历史。

**实施记录（2026-11-02）**

- `core/agent/BackgroundTaskHub`：会话级任务表 + 自有 `QThreadPool`
  （4 线程）。`{id: sa-<n>, goal, role, state, startedAt, finishedAt,
  steps, proposalCount, error, progressTail(3), 完整 SubAgentReport}`；
  状态 `queued → running → completed|failed|cancelled`。互斥 + 等待条件
  变量，`changed()` 可从任意线程发出；AIAgent 用 250ms 单发定时器合并后
  emit `backgroundSubAgentsChanged`。
- `spawn_agent` 新增 `background: bool`（默认 false）。后台分支把请求、
  service 工厂、取消令牌与角色档案快照交给 hub，`createTask` 在 hub 池上
  运行；工具立即返回 `[Sub-agent started] id=sa-N...` ack。后台运行仍经
  既有 `acquireSlot` 并发闸排队，进度经 `hub->updateProgress` 回传。
- `subagent_wait/status/cancel`（`core/tools/SubAgentControlTool`）：
  wait 默认 60s、上限 10 分钟，超时返回 success + `state=running`（不是
  失败）；status 返回状态/耗时/步数/提案数与最近进度；cancel 只翻共享
  令牌。三者与 spawn/apply_proposal 同门控注册，并在
  `SubAgentTool::refreshCatalog` 显式排除（子代理不得管理后台任务）。
- 报告取回复用 `SubAgentTool::reportOutput/proposalIndex/proposalData`：
  wait 结果与同步 spawn 同形（证据路径、`## PROPOSALS`、提案索引 +
  完整数据），`finishToolExecution` 对 `subagent_wait` 同样投影提案到
  P4.4 注册表并注入 Proposal ids。
- trace：每个后台任务一个独立 `subagent_task` 节点，metadata 带
  `taskId/goal/role/state`（白名单 + SqliteMemory 持久化键同步），状态
  变化只更新该节点；ack 节点仍只是普通 spawn tool_call。
- 生命周期（已定）：主任务结束后台任务继续；会话切换（resetSession /
  resumeSession）统一取消并清空映射；应用退出（AIAgent 析构）级联取消；
  任务表仅进程内。每会话上限 4 个；30 分钟 TTL 由 hub 的
  `QTimer::singleShot` 执行（超时翻令牌；排队中的直接归 `failed`，运行中
  等 Runner 收尾后也归 `failed` 并保留"超出 30 分钟"原因）。
- 面板：`BackgroundTasksDialog.qml` + TopBar `agents` 入口（仅在有排队/
  运行中任务时显示，角标=进行中数量）；行内 1s 本地时钟推进耗时，展开
  按需取完整报告；「停止 / 全部停止 / 清除已结束」分别接
  `AgentVM.cancelBackgroundSubAgent / cancelAllBackgroundSubAgents /
  dismissFinishedBackgroundSubAgents`。`AgentVM` 的
  `backgroundSubAgents / backgroundSubAgentActiveCount` 读活动标签的
  hub，切换标签即换数据源。
- 测试：`subagentBackgroundAckStatusWait`（ack 先返回、status=running、
  wait 超时非失败、完成后取回报告、未知 id）；`subagentBackgroundCancel-
  OneTask`（只取消目标，另一个完成）；`subagentBackgroundForkJoinThrough-
  Agent`（主循环 ack → wait → 报告回灌、面板快照、subagent_task 节点）；
  `test_background_tasks_qml`（空态、行数、标题计数、清除已结束入口）。

## 7. P4.4 提案的结构化应用

**问题**：主代理按报告里的 `find` 原文手工调用 `edit_file`。报告在主历史里
被压到 6000 字符（AIAgent.cpp:43/2494），提案一多，`## PROPOSALS` 可能被
截断；模型抄写长锚点也容易出错。

**设计**

1. `SubAgentTool` 把**完整提案**（path/rationale/edits）放进
   `ToolResult.metadata["subagentProposals"]`；`AIAgent::finishToolExecution`
   负责投影：完整数据进会话内存注册表（键 `spawn 节点 id#序号`），trace
   持久化仍只写轻量索引（P3.2 的形状不变，节点不膨胀）。**注册表仅进程内**
   （已定）：重启后回退为报告/证据工件里的文本，模型可重新派生或手工应用。
2. 新增 `apply_proposal(id)`（`RequiresConfirm`，`autoEditSafe=true`）：
   - `generatePreview` 从注册表取 find/replace，用与 `edit_file` 相同的
     `unifiedDiff` 生成确认预览；
   - `execute` 重新读取文件、重新校验锚点唯一性（文件可能已变），失败时
     复用 P3.3 的重定位提示；
   - 应用成功后标记该提案 `applied`，重复应用返回可读失败。
3. 注册表访问沿用现有线程局部模式：新增 `ProposalStoreRouter`，在
   `processNextToolCall` 的 `generatePreview` 与派发 lambda 的 `execute` 两处
   安装（GUI 线程装实时表，池线程装 `shared_ptr` 快照）。
4. 报告与应用指引改为：优先 `apply_proposal(id)`；需要改锚点或新建文件时才
   退回 `edit_file` / `file_write`。

**验收**：确认后文件按提案变化；未确认不落盘；锚点失效走重定位提示；重复
应用失败；trace metadata 仍只有索引（体积不回退）；跨会话不串提案。

**实施记录（2026-11-02）**

- `SubAgentTool` 在 `ToolResult.metadata` 增加 `subagentProposalData`
  （完整 path/rationale/edits，transient）；`finishToolExecution` 以
  `<trace 节点 id>#<n>` 为键写入 AIAgent 持有的 `ProposalStore`
  （`core/tools/ProposalStore.h`，互斥保护、仅进程内），并在报告的
  `## PROPOSALS (not applied)` 标题下注入
  `Proposal ids (pass one to apply_proposal): …#1 → app.cpp`。trace 节点仍
  只持久化原有轻量索引，正文不膨胀。
- `ApplyProposalTool`（`apply_proposal`，RequiresConfirm + autoEditSafe）：
  `generatePreview` 从注册表取完整提案生成 diff；`execute` 重新读文件、
  按顺序重放 `find` 校验（0 次附 `relocateHint`，>1 次报歧义），成功后
  QSaveFile 原子写入 + checkpoint，并标记 applied（重复应用可读失败）。
- `ProposalStoreRouter`（与 `SubAgentProgressRouter` 同型）：GUI 线程在
  `generatePreview` 前安装，派发 lambda 在池线程 `execute` 前安装；
  未安装时工具拒绝。
- 注册与 `spawn_agent` 同门控（main.cpp）：子代理关闭时一起摘除；
  子代理只读目录不会包含它（RequiresConfirm）。
- 会话切换（`resetSession`/`resumeSession`）清空注册表；id 不跨重启、
  不跨会话。报告与系统提示的应用指引从「手工 edit_file」改为「优先
  apply_proposal(id)，无 id/需改锚点时回退 edit_file」。
- 复用：`unifiedDiff` 与 `relocateHint` 抽到
  `core/tools/FileEditUtil.h`，edit_file 与 apply_proposal 同源。
- 测试：`applyProposalToolValidatesAndApplies`（无路由拒绝、预览不落盘、
  应用 + checkpoint、重复/未知 id、锚点失效、歧义）；`applyProposalPreview-
  AndApplyThroughAgent`（动态脚本服务解析报告 id → 确认弹窗 diff → 批准后
  落盘 → trace 只有索引）；`coderSameFileProposalsGetMergeHints` 增加 id
  注入与索引键断言。

## 8. P4.5 队列可见性与单任务取消

- **排队进度**：`SubAgentTool::execute` 在 `acquireSlot` 之前先发
  `phase = "queued"`（detail：`waiting for a free slot`），等待循环里按
  `kSlotWaitSliceMs` 节流更新。卡片标题显示 `spawn_agent · queued`，不与
  `step` 混淆。
- **单任务取消**：`cancelSubAgents()` 目前一把取消所有在飞 spawn 调用
  （AIAgent.cpp:1870）。新增 `cancelSubAgent(nodeId)`：`dispatchToolExecution`
  记录 `nodeId ↔ call.id`（`m_inFlightNodeIds`），ProcessCard 的「停止」
  改为 `AgentVM.cancelSubAgent(modelData.id)`。全量入口保留（工具栏/全局停止）。
- **取消语义不变**：只翻原子旗标，主任务继续；Runner 观察旗标后归类
  `Stop::Cancelled`，报告仍回填给主代理（已有测试 `subagentManualCancelKeepsPrimaryRunning`）。

**实施记录（2026-11-02）**

- `SubAgentTool::acquireSlot(cancelled, onQueued)`：无空槽时每
  `kSlotWaitSliceMs`（250ms，与取消轮询同频）回调一次；`execute` 在排队
  前取线程局部进度钩子，发出 `phase="queued"`（`step=0`，detail
  `waiting for a free slot`）。`AIAgent::applySubAgentProgress` 对 queued
  单独构造标题 `spawn_agent · queued`（不显示伪造步号），不写过程日志。
- `AIAgent::cancelSubAgent(traceNodeId)`：新增 `m_subAgentNodeCalls`
  （trace 节点 id → call.id，只登记在飞 spawn_agent）；watcher 完成与
  stop/finish/fail 各清理点同步清空。`AgentVM.cancelSubAgent(nodeId)` →
  ProcessCard「停止」只取消目标卡片；全量 `cancelSubAgents()` 保留给
  工具栏/全局路径。
- 顺带修复 P4.1 可视化的落库漏洞：`applySubAgentProgress` 的 `logChanged`
  原先只含 assistant/tool，context 事件在标题不变时会被提前 return 丢掉，
  现已纳入。
- 测试：`subagentQueuedProgressReported`（maxParallel=1 + 两个并行 spawn：
  第二个节点标题出现 `spawn_agent · queued`）；`subagentCancelOnlyTargetNode`
  （两个慢子代理，取消其一：恰好 1 个 Cancelled + 1 个报告，非法节点返回
  false，结束后映射已清理）。

## 9. P4.6 可选增强

- **角色级模型**：`SubAgentRole` 增加 `profileId`/`effort`；`spawn_agent`

- **流式回传**：Runner 目前只连 `responseReady`，`streamingChunk` /
  `reasoningChunk` 未使用。可按 200ms 节流把增量文本作为进度发（日志仍受
  50 条上限约束），降低长思考期间"只有 thinking"的空窗感。

**实施记录（2026-11-02）**

- 角色级模型：`SubAgentRole` 增加 `profileId` / `effort`（JSON 档案解析时
  剔除首尾空白；预设为空 = 沿用活动 profile）。服务工厂签名改为
  `IAIService*(profileId, effort)`，保留零参重载给测试/旧宿主；main.cpp

  同步假服务的 chunk 不会产生事件——它们发生在事件循环之前）。

## 10. 安全与边界

- 子代理仍只读；后台化不改变工具面、沙箱与确认流。`apply_proposal` 是新的
  写入口，但走既有 `RequiresConfirm` + diff 预览 + 检查点。
- 后台任务只在会话内、进程内存在；`stop()`、会话关闭、应用退出都必须级联
  取消，不允许出现"无主线程仍改文件"的路径。
- 提案注册表按会话隔离；id 伪造（不存在/已应用/属于别的会话）一律可读失败。
- 嵌套并发必须有上限（每会话 4 个后台任务 × 每轮 3 个内部并发），否则一次
  推理可能放大出十几条并发网络请求。

## 13. 曾考虑且否决的方案

1. **子代理跑在 GUI 线程**：网络事件循环与界面互相阻塞，否决。
2. **同一会话并行两条主循环**：消息历史交错、请求在飞无法归因，否决。
3. **完成时向主历史注入消息来实现后台化**：见 §6.4（顺序、恢复、审计）。
4. **并行化 `propose_edit`**：`QThreadStorage` 汇聚槽按线程隔离，且提案顺序
   应稳定；保持运行线程串行。
5. **放开子代理递归派生**：并发与 token 放大不可控，深度保持 1。
6. **多个子代理共享一个 IAIService**：服务实例只有一条在途请求；每个运行
   独立实例是现有并发单位，不改。

## 14. 产品决策（已定，2026-11-02）

1. 主任务结束时后台子代理：**继续跑**（可稍后取回），TTL 30 分钟；会话关闭
   或应用退出时取消。
2. `spawn_agent` 的 `background` 默认值：**false**。由工具描述与系统提示
   引导模型对长耗时、无依赖的任务主动使用 `true`。
3. 提案注册表：**仅进程内**。重启后回退为报告/证据工件里的文本，允许模型
   重新派生或手工应用；不新增 SQLite 表。
4. 后台任务：**增加独立面板**（顶栏入口 + Dialog，见 §6.5），trace 卡片作为
   时间线保留。
