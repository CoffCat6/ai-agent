## 2. G1 索引补齐 + schema 版本化（lite）

### 2.1 待修复项

- `src/core/memory/SqliteMemory.cpp:194-204` — messages 表建表 DDL，**无任何二级索引**（全库仅 audit/trace_nodes/usage/token_usage 有索引，见 :279、:309、:326、:362-368）。
- `src/core/memory/SqliteMemory.cpp:247-254` — sessions 表 DDL；`pinned/archived` 为后续 ALTER 补列（:413-418），排序字段无索引。
- `src/core/memory/SqliteMemory.cpp`（FTS 回填语句）— 每次启动执行 `id NOT IN (SELECT rowid FROM messages_fts)`，对 messages 全表扫描。

### 2.2 实际问题

messages 是**唯一随使用量无界增长、且被高频按会话查询的主表**。全部命中路径都按 `session_id` 过滤：`loadMessages`（:703-711，`WHERE session_id = ? ORDER BY timestamp DESC, rowid DESC`，模型切换时一次拉 2000 条）、`deleteMessagesFrom`（:742-745）、`lastUserMessageId`、`clear`、`deleteSession`、短词搜索计数（:816，已有 5 万行熔断）。无索引时每条查询都是全表扫描，消息量到万级后线性恶化——这是本方案性价比最高的一条。sessions 同理：`listSessions`（:1152-1153）每次侧栏刷新对全部会话按 `pinned DESC, updated_at DESC` 排序。

FTS 回填的 `NOT IN (SELECT rowid FROM messages_fts)` 在触发器已保证同步的稳态下是纯浪费，但每次启动都对 messages 全扫一遍，库大后拖慢启动。

### 2.3 修复后的改善

- 修复前：万级消息后 `loadMessages`/侧栏刷新为全表扫描；FTS 回填每次启动 O(messages)。
- 修复后：按会话查询走索引定位（SQLite 索引条目隐式以 rowid 结尾，`(session_id, timestamp)` 索引天然支持 `ORDER BY timestamp DESC, rowid DESC` 的反序扫描）；FTS 回填借 schema 版本标记只在老库升级时执行一次，稳态启动零扫描。
- 代价（负面）：写放大（messages 每次插入多维护一条索引项——聊天写入频率下可忽略）；新索引需要一次 `ANALYZE` 让查询计划器感知（随版本标记只在升级路径执行一次）。

### 2.4 如何修复

**① `createTables()` 内追加两条索引 DDL**（沿用 `execDdl` 纪律）：

```cpp
execDdl(query, "CREATE INDEX IF NOT EXISTS idx_messages_session_ts "
               "ON messages(session_id, timestamp)",
        "create messages session index");
execDdl(query, "CREATE INDEX IF NOT EXISTS idx_sessions_pinned_updated "
               "ON sessions(pinned, updated_at)",
        "create sessions list index");
```

不建 `(session_id, id)` 变体：`deleteMessagesFrom` 的 `id >= ?` 在索引定位到会话子集后代价可控，避免双索引写放大。

**② schema 版本化（lite）**：`initDatabase()` 开头读 `PRAGMA user_version`：

- `user_version == 0`（老库或新库首次建表）：走完整初始化——建表/补列/迁移/FTS 回填，末尾对新索引执行一次 `ANALYZE`，然后 `PRAGMA user_version = 1`。
- `user_version >= 1`：跳过 FTS 回填与 `ANALYZE`；`CREATE ... IF NOT EXISTS` 与幂等补列**全部保留**（执行成本低，不因版本标记冒险）。

不改迁移架构（现有"每次全量幂等"机制对新 DDL 仍然生效），只把**唯一一条 O(messages) 的稳态开销**挂到版本门上。

**③ 回归测试（`tests/test_memory.cpp`）**：

- 索引存在性：`databaseForTest()` 执行 `EXPLAIN QUERY PLAN SELECT ... FROM messages WHERE session_id = ? ORDER BY timestamp DESC`，断言计划含 `idx_messages_session_ts`（对 sessions 的列表查询同理）。
- 老库升级：手工构造无索引、`user_version=0` 的库文件 → `SqliteMemory` 打开 → 断言索引存在且 `user_version == 1`；二次打开断言 FTS 回填被跳过（可通过在 messages_fts 里塞一条孤儿行、重启后仍存在来证明回填未执行）。

## 3. G2 WAL + synchronous=NORMAL

### 3.1 待修复项

`src/core/memory/SqliteMemory.cpp:78-81` — 连接初始化只设 `PRAGMA busy_timeout = 5000`，journal 保持默认 rollback 模式，未设置 synchronous。

### 3.2 实际问题

Batch 29 的结构是**每个会话标签各持一条连接写同一个库文件**（`main.cpp:422`，P0/F2 后仍如此），rollback journal 下读写互斥范围大：一个标签在 GUI 线程做流式写（docs/22 §F3 分析过的 10Hz `saveTraceNode` upsert、每轮 audit/token_usage 多行写入）时，另一标签 GUI 线程的读操作（`listSessions` 等）要等锁释放，最坏撞满 busy_timeout 的 5 秒。同时 rollback 模式每条 autocommit 语句都触发 fsync，流式路径的写放大直接落在 GUI 帧预算里。

### 3.3 修复后的改善

- 修复前：跨标签读写互斥最坏 5 秒；逐语句 fsync。
- 修复后：WAL 模式下读不阻塞写（读者读快照，写者追加 WAL）——多标签并行的互斥窗口收敛到 checkpoint；`synchronous=NORMAL`（WAL 官方推荐搭配）把 fsync 推迟到 checkpoint 时刻，掉电最多丢失最后一个已提交事务、**不会损坏数据库**。
- 代价（负面）：出现 `-wal`/`-shm` 附属文件——**裸拷贝 .db 文件不再是有效备份**，D1 因此必须走 `VACUUM INTO`（见 §8.4 设计依据）；WAL 不支持网络文件系统（应用数据在本地 AppData，无影响）。

### 3.4 如何修复

`SqliteMemory::SqliteMemory` 打开连接后追加（每连接执行，幂等——journal_mode 是库文件的持久属性，重复设置无副作用）：

```cpp
// docs/23 G2: WAL — 并行标签的读不阻塞写；NORMAL 在 WAL 下把 fsync
// 推迟到 checkpoint，掉电不损坏库（SQLite 官方推荐搭配）。
QSqlQuery pragma(m_db);
pragma.exec("PRAGMA journal_mode = WAL");
pragma.exec("PRAGMA synchronous = NORMAL");
```

**回归测试（`tests/test_memory.cpp`）**：打开后 `PRAGMA journal_mode` 返回 `wal`；既有"多实例/多连接写同一库"的并发冒烟保持全绿（test_memory 现有多连接用例天然覆盖）；test_chat_workflows 全量回归（流式写路径切换到 WAL 后行为不变）。

## 4. G3 token_usage / audit_log 保留策略 + 定时 prune

### 4.1 待修复项

- `src/main.cpp:491` — `memory->pruneUsage()` 仅启动时执行一次（默认 30 天/10000 行，`SqliteMemory.h:127`）。
- 全库 grep 无 `DELETE FROM audit_log` / `DELETE FROM token_usage`——**两张表完全没有保留策略**。token_usage 每次 LLM 请求一行、25+ 列（`SqliteMemory.cpp:333+`），是增长最快的表；audit_log 的 `arguments` 存全量工具参数。

### 4.2 实际问题

托盘常驻/关闭最小化到托盘是本产品的常态使用方式（docs/20 工作流 B 落地的能力）——进程数天不重启意味着唯一的清理时机（启动）不会到来，usage_log 无限超出策略；token_usage 与 audit_log 则**永远**不清理。三者叠加：数据库体积与聚合查询（用量页的 `tokenStatsDetailed/costStats/quotaStatus` 是同步 Q_INVOKABLE）随使用时长单调恶化。

### 4.3 修复后的改善

- 修复前：三张表无界增长（usage 仅靠重启收敛）。
- 修复后：启动 + 每 6 小时定时收敛一次；token_usage/audit_log 按天保留（默认 90/30 天，0 = 永久保留），用户可在设置页调整或关闭。
- 代价（负面）：审计链默认 30 天后消失——docs/21 把"审计链凭 request_id 串起请求/执行/结果"列为卖点，故保留天数必须可配置且默认值保守；定时器回调是空转成本可忽略（两条带索引的 DELETE）。

### 4.4 如何修复

**① 新设置键**（`SettingsSchema.cpp`，沿用 `keyDef` 账本；`test_settings` 锁条目）：

```cpp
keyDef(QStringLiteral("memory/auditRetentionDays"), 30, SettingValueType::Int),
keyDef(QStringLiteral("memory/tokenRetentionDays"), 90, SettingValueType::Int),
```

0 = 永久保留。UI 挂 `MemoryPage.qml`（数据管理页，与配额设置同区），中文文案走 qsTr。

**② `SqliteMemory` 新增两个 prune**（与 `pruneUsage` 同构；`idx_audit_ts`、`idx_token_usage_ts` 已存在，DELETE 走索引）：

```cpp
int pruneAudit(int keepDays);       // DELETE FROM audit_log WHERE timestamp < cutoff
int pruneTokenUsage(int keepDays);  // DELETE FROM token_usage WHERE timestamp < cutoff
```

keepDays <= 0 直接返回 0（永久保留）。

**③ `main.cpp` 定时器**（parent 到 app，进程生命期）：

```cpp
auto* pruneTimer = new QTimer(&app);
pruneTimer->setInterval(6h);
QObject::connect(pruneTimer, &QTimer::timeout, &app, [usageMemory, settings, &app]() {
    QMetaObject::invokeMethod(&app, [usageMemory, settings]() {   // SQLite 在 GUI 线程
        usageMemory->pruneUsage();
        usageMemory->pruneAudit(settings->auditRetentionDays());
        usageMemory->pruneTokenUsage(settings->tokenRetentionDays());
    }, Qt::QueuedConnection);
});
pruneTimer->start();
```

启动时保留现有 `pruneUsage()` 调用并顺带执行两个新 prune（首轮收敛不等 6 小时）。6 小时而非 24 小时：长驻进程收敛更及时，代价可忽略。

**④ 回归测试（`tests/test_memory.cpp`）**：插入跨期行（cutoff 前后各含边界值）→ prune 断言保留/删除边界精确；keepDays=0 不删任何行；多轮插入 + prune 幂等。

## 5. G4 write_file 假成功修复

### 5.1 待修复项

`src/core/tools/ToolRegistry.cpp:122-143`（`FileWriteTool::execute`）——普通 `QFile` 非原子写，`QTextStream::flush()` 与 `file.close()` 的返回状态不检查。

### 5.2 实际问题

磁盘满/配额超限时：`QTextStream` 缓冲写失败被吞、`close()` 的错误被吞，工具**仍返回 "File written successfully: … (N bytes)"**——模型基于假成功继续后续步骤（如 edit_file 校验刚写入的文件），用户在 UI 上也看到成功。对照 `edit_file`（:218-231）已是 QSaveFile 原子写 + 短写/commit 显式报错，注释还专门写明"edit_file 面向已存在文件，损坏代价更高"——write_file 是遗留的不一致。

附带问题：write_file 用 `QIODevice::Text` 模式（Windows 下 `\n` → `\r\n` 翻译），而 edit_file 写原始 UTF-8 字节。两个工具混用会产生混合行尾文件——`editFileCrlfBoundary` 用例已证明 edit_file 按**精确字节**匹配 `old_string`，模型用 `\n` 写的 old_string 对上 write_file 产出的 CRLF 文件会意外 not-found。

### 5.3 修复后的改善

- 修复前：磁盘满/配额时假成功误导模型与用户；与 edit_file 行尾语义不一致。
- 修复后：QSaveFile 原子写——短写（磁盘满）与 commit 失败都返回携带 `errorString` 的失败结果；与 edit_file 统一为"字节进出"，行尾由模型内容决定（通常 `\n`），跨工具操作同一文件不再有行尾漂移。
- 代价（负面）：**行为变化**——Windows 上 write_file 产出的文件从 CRLF 变为 LF。对"write_file 产出后由编辑器打开"的场景无实质影响（编辑器都兼容 LF）；对"write_file 后 edit_file 同一文件"的场景是修复而非破坏。方案在提交信息与用户手册中明示此变化。

### 5.4 如何修复

`FileWriteTool::execute` 写入段替换为与 edit_file 相同的模式：

```cpp
// docs/23 G4: 原子写 + 显式错误上报，与 edit_file（Batch 21 A2）同模式。
// 不再用 QIODevice::Text：字节进出与 edit_file 统一，避免两工具
// 产出混合行尾文件（edit_file 按精确字节匹配 old_string）。
const QByteArray bytes = content.toUtf8();
QSaveFile out(path);
if (!out.open(QIODevice::WriteOnly))
    return ToolResult::fail("Cannot open file for writing: " + out.errorString());
if (out.write(bytes) != bytes.size()) {
    out.cancelWriting();
    return ToolResult::fail("Short write (disk full/quota?): " + out.errorString());
}
if (!out.commit())
    return ToolResult::fail("Failed to commit atomic write: " + out.errorString());
```

磁盘满的物理模拟在单测里不可靠，不硬造：该代码模式与 edit_file 逐行同构，短写/commit 分支由既有 `editFile*` 套件的模式覆盖。新增回归（`tests/test_sandbox.cpp`，工具经 ToolRegistry 驱动）：

- **行尾往返**：`write_file` 写入含 `\n` 的内容 → `read_file` 读回逐字节一致（锁死 LF 语义不回归）；
- **目标为目录**：`write_file` 指向已存在目录 → 失败且错误含 open 错误串（覆盖"open 失败要报错"路径，防退化成假成功）。

## 6. G5 loadMessages 静默失败修复

### 6.1 待修复项

`src/core/memory/SqliteMemory.cpp:717-732`（`loadMessages`）——`query.exec()` 失败时无 else 分支，静默返回空数组。

### 6.2 实际问题

全文件的查询普遍遵循"exec 失败 → `qWarning` 带 `lastError`"的纪律（`execDdl` 注释甚至写明"schema 语句不许静默失败"），唯独 `loadMessages` 漏了。后果是**用户可见且不可诊断**：查询失败（磁盘 IO 错误、库损坏、并发异常）时用户看到"这个会话的历史消失了"，而日志里一个字都没有——排查无从下手。这是 P0 审查（docs/22 前置分析）确认的全文件唯一缺口。

### 6.3 修复后的改善

- 修复前：查询失败静默返回空，日志无痕。
- 修复后：与全文件纪律一致——失败记 `qWarning` 带 `lastError().text()`；返回值语义不变（空数组），调用方无需改动。
- 代价（负面）：无（一行告警）。

### 6.4 如何修复

```cpp
    if (query.exec()) {
        ...（现有 while 循环不动）
    } else {
        qWarning() << "Failed to load messages:" << query.lastError().text();
    }
```

**回归测试（`tests/test_memory.cpp`）**：`databaseForTest()` 执行 `DROP TABLE messages` → `loadMessages` 返回空数组且不崩溃（失败路径被触达）；重建表后恢复正常。告警本身的存在性靠代码评审与该测试触达的失败分支保证。

## 7. G6 恢复路径预算缺口 + clear() 漏删 trace_nodes

### 7.1 待修复项

- `src/core/rag/RagService.cpp:171-196`（`restorePersistedDocument`）——锁内直接 `dropDocumentLocked` + 入库，**没有** `m_maxTotalChunks` 预算检查；对照 `ingestDocument`（:123-124）与 `ingestRestoredDocument`（:155-156）都有。
- `src/core/memory/SqliteMemory.cpp:1095-1107`（`clear`）——删 messages 与 episodic，**漏删 trace_nodes**（对照 `deleteSession` :1249+ 是四表级联）。当前无调用方，属潜伏陷阱。

### 7.2 实际问题

知识库总量预算（默认 4096 段，REL-1003）只在导入/重嵌路径生效。重启恢复路径把 SQLite 里的段原样装回内存时**整体绕过预算**：若用户把预算设置调小、或库文件经外部途径超出预算，恢复后内存中的段数超出上限而检索、UI 计数均不知情——预算不变量被静默打破。clear() 漏删的后果：一旦未来有调用方（"清空当前会话"语义很自然会长回来），会话消息清了但思考轨迹残留，重开会话出现"幽灵轨迹"，且这类数据不一致在 SQLite 层没有任何约束兜底。

### 7.3 修复后的改善

- 修复前：预算只在导入侧成立，恢复侧可静默突破；clear() 语义与 deleteSession 不对称。
- 修复后：预算成为全路径不变量；恢复期超预算文档**跳过装载**（持久层不动，可随时删减后重嵌）并逐条告警；clear() 三表对齐。
- 代价（负面）：预算调小后重启，超出部分的知识库文档不在内存（检索不到）——但这是预算语义的正确呈现，且有显式日志指路。

### 7.4 如何修复

**① `restorePersistedDocument` 锁内补预算**（与 `ingestRestoredDocument` 同构）：

```cpp
    {
        QMutexLocker lock(&m_mutex);
        if (generation != m_restoreGeneration) return false;
        // docs/23 G6: 恢复路径同样受总量预算约束（REL-1003 全路径不变量）。
        const int current = totalChunksLocked() - dropDocumentLocked(sourceName);
        if (current + chunks.size() > m_maxTotalChunks) {
            qCWarning(lcRag) << "Restore skipped (budget):" << sourceName
                             << chunks.size() << "chunks exceed remaining budget";
            return false;
        }
        Document doc;
        ...
    }
```

注意 `dropDocumentLocked` 的调用顺序与 ingest 路径保持一致（先扣同名旧档再判断）。启动恢复循环（`main.cpp:513-521`）对返回 false 的文档聚合计数，循环结束输出一行汇总告警（"N 份文档因预算跳过"），避免刷屏。

**② `clear()` 补一行**（含注释说明与 deleteSession 对齐）：

```cpp
    query.prepare("DELETE FROM trace_nodes WHERE session_id = ?");
    query.addBindValue(sessionId);
    if (!query.exec())
        qWarning() << "Failed to clear trace nodes:" << query.lastError().text();
```

**③ 回归测试**：

- `tests/test_rag.cpp`：压小 `m_maxTotalChunks` → 导入文档 A、B（A 占满预算）→ 走恢复路径装载 B → 断言 B 被拒、A 仍在、检索不受影响；恢复 A 的持久化段 → 成功。
- `tests/test_memory.cpp`：写入消息 + trace 节点 → `clear()` → 断言三表皆空。

## 8. D1 数据库备份（启动自动 + 手动）与恢复预览

### 8.1 待修复项

全库唯一与"备份"相关的是 `SettingsBackup.cpp`——**设置 JSON 导出**，readme 明示"这不是数据库的完整备份"。数据库（会话/轨迹/审计/知识库，`%APPDATA%/NexusAI/NexusAI/nexusai_memory.db`）没有任何备份机制。

### 8.2 实际问题

数据库是本应用全部用户数据的单点：磁盘故障、库损坏、误操作（配合 G7 落地前的批量删除）、升级事故都没有回退手段。docs/20 §6.2 的"启动自动备份"规划了但未实施；docs/21 把它列为后续批次第 1 项。P1a 先交付**备份 + 预览**，恢复（D2）独立子批——备份先行的价值：从本批合入后的第一次启动起，用户数据就不再是无状态裸奔。

### 8.3 修复后的改善

- 修复前：单文件裸奔，任何损坏即全损。
- 修复后：每次启动自动产生一致快照并轮转保留 N 份（默认 3）；设置与备份页可随时手动备份（不限量）与预览任意备份文件的内容概况（会话数/消息数/知识库文档数/时间范围）。
- 代价（负面）：每份备份 ≈ 当前库文件大小（消息含 base64 附件后可观，保留 3 份 × 3 倍占用）；启动多一次 VACUUM INTO（库大时秒级，在后台线程执行不阻塞启动）。

### 8.4 如何修复

**① 备份机制：`VACUUM INTO`**（SQLite ≥ 3.27；Qt 6.9 内置的 SQLite 版本远高于此）：

```cpp
// SqliteMemory 新增：
bool backupTo(const QString& targetPath) {
    QSqlQuery query(m_db);
    query.prepare("VACUUM INTO ?");
    query.addBindValue(targetPath);
    if (!query.exec()) { qWarning() << ...; return false; }
    return true;
}
```

选型依据：一条 SQL 得到**一致性快照**（内部读事务），天然涵盖 WAL 中未 checkpoint 的内容，不需要处理 `-wal`/`-shm` 附属文件（对比"checkpoint 后裸拷贝"方案的竞态面），产物是干净的单文件库（顺带完成碎片整理）。G2 落地 WAL 后这是唯一正确的文件级备份方式。

**② 触发与轮转**：

- 启动自动备份：`main.cpp` 在主 memory 打开之后、后台知识恢复之前，`QtConcurrent::run` 后台执行（不阻塞启动；单实例锁 QLockFile 已保证无并发写者）。设置键 `memory/backupOnStartup`（Bool，默认 true）。
- 手动备份：设置与备份页（SettingsBackupPage.qml）按钮，同步执行（用户显式等待）。
- 轮转：设置键 `memory/backupKeepCount`（Int，默认 3）；自动备份产物按时间戳排序保留最新 N 份，手动产物不参与轮转（用户自管）。目录：`%APPDATA%/NexusAI/NexusAI/backups/nexusai_memory_YYYYMMDD_HHMMSS.db`。
- 失败语义：备份失败只 `qWarning` + 设置页显示上次备份状态，**绝不阻断启动或使用**（备份是增强不是门槛）。

**③ 恢复预览**（只读，零生命周期扰动）：设置与备份页"选择备份文件 → 预览"：

```cpp
// 对备份文件建立只读独立连接（QSQLITE_OPEN_READONLY），读取：
// sessions 总数、messages 总数、最新消息时间、知识库文档数。
QSqlDatabase::addDatabase("QSQLITE", previewConnName);
db.setDatabaseName(backupPath);
db.setConnectOptions("QSQLITE_OPEN_READONLY");
```

预览结果填充确认对话框（为 D2 的恢复确认复用）。预览连接用后即毁（P0/F2 的 MEM-702 纪律）。

**④ 新设置键 ×2**：`memory/backupOnStartup`、`memory/backupKeepCount`，入 ledger，UI 挂 SettingsBackupPage（含"上次自动备份时间"状态行）。

**⑤ 回归测试（`tests/test_memory.cpp` + `tests/test_settings.cpp` 账本）**：

- `backupTo` 产物：新 `SqliteMemory(path)` 打开备份文件，比对源库与备份的 sessions/messages/知识库行数一致；`PRAGMA quick_check` 返回 ok。
- 轮转：造 5 份备份 → 轮转后剩 N 份且是最新的 N 份。
- 预览连接只读：对预览连接执行写语句必须失败。
- 设置键账本：`test_settings` 补两条新键断言（沿用既有模式）。

## 9. D2 数据库恢复（P1b 独立子批——设计定稿，实施另排）

docs/21 要求：*"恢复数据库涉及全部 SQLite 连接及后台任务的生命周期，应独立实现并进行失败回滚验证。"* 本节把设计定稿，实施时照此执行并专项验证。

### 9.1 流程设计

```
用户在备份页选择备份 → 预览（D1 只读连接）→ 确认对话框
  1. AgentViewModel：停止全部在跑任务（逐 tab stop()）+ 关闭全部标签
     （P0/F2 后 per-tab SqliteMemory 随标签析构，连接自然回收）
  2. 主 memory（main.cpp:235，被 agentVM/agent/episodic/知识库恢复共用）
     与 usageMemory（:479，即同一实例）执行 reopen()
     —— SqliteMemory 新增 reopen()：close → removeDatabase → 重走
        open + PRAGMA + initDatabase；对象指针不变，Activity sink、
        modelConfigurator 等捕获的裸指针全部保持有效
  3. 文件替换（此时尚无任何打开连接）：
     a. 把当前库拷为 <db>.pre-restore（回滚保底）
     b. 备份文件拷为 <db>.restore-tmp → PRAGMA quick_check 校验
     c. 删除现存 <db>-wal / <db>-shm（旧 WAL 混入新库文件会损坏）
     d. remove(<db>) + rename(<db>.restore-tmp → <db>)
        （QFile::rename 目标存在时失败，必须先 remove；两步间隙靠
          .pre-restore 保底）
  4. reopen() 重开连接
  5. RagService：公开 bumpRestoreGeneration()（现有 m_restoreGeneration
     由 clear()/removeDocument() 内部递增，恢复路径需要外部触发），
     重新执行启动恢复流程（main.cpp:497-521 的知识库恢复段提取为可复用函数）
  6. AgentViewModel：refreshSessions() 全量刷新 + 当前标签重载消息
```

### 9.2 失败回滚

`restore-tmp` 阶段任何失败（拷贝中断、quick_check 不过）→ 原库文件未动，删除临时文件、重启连接、UI 报错即可；`rename` 之后的失败理论上只剩 reopen 失败 → 用 `.pre-restore` 覆盖回去再重开。启动时若发现残留 `.pre-restore`（上次恢复中断），提示用户并保持现状不自动动库。

### 9.3 专项验证（P1b 验收线）

- test_chat_workflows 风格：两个标签有在跑任务 + 排队审批时触发恢复 → 任务被停止封口、无悬垂回调；
- 恢复中途注入拷贝失败 → 原库数据不变、UI 可继续使用；
- 恢复成功 → 会话/知识库与备份一致、新消息正常写入、重启后无 `.pre-restore` 残留;
- 单实例锁全程持有（恢复不释放 QLockFile，杜绝双写窗口）。
