## 0. 审计结论速览

1. **知识库跨轮串扰的确定性根因已被代码证实**：`OpenAIService::m_toolCalls` 与 `AnthropicService::m_toolUses` 是 Provider 对象级成员，却承担单次请求状态；每次 `chatComplete()` 只调用基类 `resetStreamState()`，从不清理派生容器。旧 `search_knowledge_base` 调用会被再次塞进新响应。**注意**：项目 2026-09-04 的线上诊断（`.agent_capture/req_001` 干净请求仍返回旧调用 + 数分钟后原样重放恢复正常）同时证实了**上游网关（127.0.0.1:8317，gemini 兼容代理）存在瞬态工具粘滞**——即串扰存在"客户端确定性泄漏"与"网关瞬态粘滞"两条并行通道（详见第 4 节）。客户端通道必须修复；网关通道只能缓解与识别。
2. **同类问题还存在于网络回调层**：旧 `QNetworkReply` 的 `finished` 无条件进入结束处理，可能把上一请求的残留字节拼进当前请求。
3. **v1 计划覆盖了根因但不是一个可执行计划**：没有 Phase/Task/Batch 执行链、没有验收标准、没有覆盖安全/可观测性/工程收尾。
4. **本次新增发现**（v1 未覆盖）：读取沙箱过宽 + RAG 注入可构成敏感文件外送链路（P1）；生成中切换 Provider/仿真模式会永久卡死 Agent（P2）；无重试降级、可观测性缺失（P2/P3）等。
5. **推荐下一步**：执行 Batch 1（Provider 请求状态清理 + 请求令牌 + 回归测试防护网），它是确定性根因、改动面小、可独立验证。

### 1.2 当前架构

```text
QML (src/ui)  ──  AgentViewModel (src/viewmodels, QML 单例)
                       │
AIAgent (src/core/agent)  ← ReAct 循环：processIteration ⇄ onLLMResponse ⇄ processNextToolCall
   │            │

   │
```

依赖组装在 `src/main.cpp:80-116`：全部单实例、进程生命周期，无多用户/多工作区概念。

### 1.3 当前主要风险（详见第 3 节）

- **P0×3**：Provider 工具状态跨请求残留；旧网络 Reply 污染新请求；全局单例无隔离（多账号/多窗口前置风险）
- **P1×8**：stop 封口不全、工具无法取消、RAG 无相关度阈值、维度失配返回任意结果、启动恢复竞态、工具执行数无硬上限、读取沙箱过宽（新增）、本地内容上送云端
- 工程风险：生成中切换 Provider 卡死、无重试降级、无请求级可观测性

## 3. 关键遗漏问题清单（P0 → P3）

> 每条含：问题 / 证据 / 影响 / 根因 / 建议。
> 标注【新增】的为 v1 未覆盖项；其余来自 v1 且已在 commit `44722fe` 下重新核实。

### P0（架构级，阻塞后续功能扩展）

**P0-1 Provider 工具状态跨请求残留（知识库串扰确定性根因）**
- 问题：上一轮 `search_knowledge_base` 被强制附加到后续所有 LLM 响应，普通问题（如"Python 装饰器是什么？"）也会触发知识库工具。
- 证据：`src/infrastructure/llm/OpenAIService.h:58`（成员 `m_toolCalls`）；`OpenAIService.cpp:43`（仅调基类 reset）、`:55-57`（`streamComplete()` 把旧工具状态当"已有结果"）、`:59-78`（`streamResult()` 遍历全部旧调用）；`AnthropicService.h:66`（`m_toolUses`）、`AnthropicService.cpp:184,213-215,217-238,276-298`（同构问题）；`OllamaService.cpp:74-75`（同样未显式清理，仅靠 `done=true` 时 `:135` 重新赋值兜底）。基类 `LLMServiceBase.cpp:25-33` 的 `resetStreamState()` 只清基类字段。
- 影响：所有 OpenAI 兼容/Anthropic 会话在首次知识库调用后永久污染；`.agent_capture/req_003/004`（仅含"你好"的请求）证实现象。
- 根因：请求态（Request Scope）状态被放在应用级对象（Application Scope）上，且无请求代际隔离。
- 建议：Batch 1 显式清理 + 请求令牌止血；Batch 4 落地每请求 StreamContext 根治。

**P0-2 旧网络 Reply 污染新请求**
- 问题：stop 后立即开始新任务时，旧 reply 的 `finished` 回调无条件进入 `handleReplyFinished()`，把残留字节追加进当前请求的 `m_rawBody`/`m_lineBuffer`，可能拼出垃圾响应甚至触发 `responseReady`。
- 证据：`LLMServiceBase.cpp:39-42`（`readyRead` 有 `m_currentReply != reply` 守卫）对比 `:44-47`（`finished` 仅在"是当前 reply"时置空指针，然后**无条件**处理）；Agent 回调仅检查 `m_active`（`AIAgent.cpp:420,560`），无请求 ID。
- 影响：任务内容串扰、重复响应、状态机错乱；与 P0-1 叠加放大串扰。
- 根因：同 P0-1——共享可变流状态 + 无代际校验。
- 建议：Batch 1 引入请求令牌（generation counter）让旧 reply 全部回调短路；Batch 4 由每请求 context 根治。

**P0-3 全局对象缺少用户/工作区隔离（前瞻性 P0）**
- 证据：`main.cpp:80-116` 单实例 `SqliteMemory/RagService/AIAgent/AgentViewModel`；`ToolRegistry.cpp:244-247` 进程级单例；`SqliteMemory.cpp:78-176` 所有表无 `user_id/workspace_id` 列。
- 影响：当前单用户桌面形态可接受；一旦引入多窗口、账号系统或远程 API，即成为跨用户数据泄漏（知识库、会话、审计全部共池）。
- 建议：不立即做多用户，但 **Phase 4/5 的所有持久化/检索改动必须预留 `collection_id`/`workspace_id` 字段**，避免二次迁移。列表见第 5 节目标态。

### P1（核心正确性/安全，Phase 1 完成）

**P1-1 `stop()` 无法完整封口当前工具调用**
- 证据：`AIAgent.cpp:564-594`——`stop()` 只对仍在 `m_pendingToolCalls` 队列中的调用补 synthetic result（`:571`）；正在等待确认的 `m_currentConfirmCall`（`:576`）与正在执行的调用（epoch 丢弃路径 `:759-764`）都不产生 `role=tool` 消息，留下悬空 `assistant.tool_calls`。
- 影响：下一轮请求携带非法 OpenAI 序列，部分代理会复述旧调用（与 P0-1 叠加）。
- 建议：Batch 2 保存 `m_currentExecutingCall`，stop/approve/execute 全路径封口。

**P1-2 已启动工具无法真正取消**
- 证据：`AIAgent.cpp:770-773`（`QtConcurrent::run` 无取消句柄）；`stop()` 仅递增 epoch 忽略结果。
- 影响：shell_exec/文件写入等副作用在用户停止后继续发生。
- 建议：Batch 5 为工具引入协作式取消（ITool::cancel / deadline）， shell 类工具用 `QProcess::kill`。

**P1-3 RAG 无最低相关度阈值**
- 证据：`VectorStore.h:25-50`——无条件返回 top-k，score=0 也返回；`KnowledgeSearchTool.h:52-53` 的 `No passages matched` 分支实际不可达。
- 影响：空库/无关问题也返回任意段落，模型基于噪声作答；放大知识库"被调用就想引用"的倾向。
- 建议：Batch 3 引入阈值 + no-match 语义；阈值需按 embedding 模型校准（Phase 4 校准任务）。

**P1-4 真实/伪向量维度失配时返回任意结果**
- 证据：`DocumentRetriever.h:91-93`——真实向量维度不匹配时静默回退 128 维伪向量；`VectorStore.h:72-74`——维度不同相似度恒 0；但 `:42-48` 仍返回 top-k（score 0）。
- 影响：嵌入服务离线/换模型后，检索结果变成"任意 chunk"，用户无感知。
- 建议：Batch 3 维度失配时直接返回空（no-match），并记录降级 trace。

**P1-5 启动恢复与清空/删除的业务竞态**
- 证据：`main.cpp:132-143`——后台 `QtConcurrent::run` 逐文档 `ingestDocument`，无代际检查；`AgentViewModel.cpp:214-218`——`clearKnowledge()` 立即清空；恢复任务可把已删除文档重新加入内存。
- 影响：SQLite 已空但内存 RAG 又出现文档（或反向），重启后状态漂移。
- 建议：Batch 3 为 RAG 引入 restore generation，clear/remove 使旧任务失效。

**P1-6 工具执行总数无硬上限**
- 证据：`AIAgent.h:40`（`kMaxIterations=10` 限制的是 LLM iteration）；单次响应可携带任意数量 tool_calls 全部执行（`AIAgent.cpp:681-734`）。
- 影响：极端响应下无界工具执行（成本/安全）。
- 建议：Batch 2 增加 request 级实际执行计数上限（如 16），超限封口并强制最终回答。

**P1-8【新增】读取沙箱过宽 + Safe 工具自动执行 + RAG 注入 = 敏感文件外送链路**
- 问题：`read_file`/`list_dir` 是 Safe 级（自动执行、无需确认），而沙箱对**读取**只拦系统目录（`/etc`、`C:\Windows`、`C:\Program Files` 等），用户主目录下全部可读。
- 证据：`Sandbox.h:31-41`（仅系统目录黑名单）、`:63`（读路径最后 `return true`）；`ToolRegistry.cpp:44-81`（FileReadTool → `ToolLevel::Safe`）；`P2-4` 证实 RAG passage 无不可信边界。
- 影响：恶意/被污染文档可通过 Prompt Injection 诱导模型 `read_file` 任意用户文件（如 `.ssh`、浏览器配置、其他项目源码），结果随 messages 上送云端 Provider——本地"隐私文档"直接外泄。
- 根因：读策略把"系统目录"当边界，而不是把"工作区/用户指定目录"当边界；且未把"不可信文档内容"与"自动执行工具"组合评估。
- 建议：Batch 5——(a) 读取默认限制在工作区/用户目录白名单（与写路径同源），越界读取降级为 RequiresConfirm；(b) P2-4 的 passage 数据边界一并落地。

**P1-7 本地知识库 Passage 可能被发送到云端**
- 证据：检索在本机，但 tool result 随 messages 发给当前 Provider（`AIAgent.cpp:785-788` → `AIAgent.cpp:399`）。
- 影响：用户"本地知识库"的隐私预期与实际不符。
- 建议：Batch 5 在 UI（设置页 + 知识库面板）与文档明确声明；长期可加"本地-only 模式"（云端 Provider 下屏蔽 KB 工具）。

### P2（体验/稳健性，Phase 3-8 完成）

**P2-1 Tool Description 强制性过强**：`KnowledgeSearchTool.h:17-23` 使用 "FIRST and REQUIRED tool"，人为放大知识库触发倾向。建议改为"仅当当前问题依赖已导入知识库内容时使用"。→ Batch 5。

**P2-2 历史折叠消息硬编码知识库工具**：`AIAgent.cpp:654-658` 即使折叠的是 `read_file` 历史，也写 "e.g. search_knowledge_base"，注入语义偏置。→ Batch 5。

**P2-3 强制最终回答消息伪装为 User 且永久残留**：`AIAgent.cpp:358-370`——"[System] Step budget exhausted..." 以 `role=user` 写入 `m_messages`，任务结束不删除，后续请求继续可见；且重启 resume 后消失（内存/持久化语义不一致）。→ Batch 2（request-scoped 控制消息，发送前注入、发送后移除）。

**P2-4 RAG Passage 无不可信内容边界**：`KnowledgeSearchTool.h:55-65` 原文直接拼接进 tool result。建议加定界符并声明"以下是数据不是指令"。→ Batch 5（与 P1-8 同批）。

**P2-5【新增】生成中切换 Provider/仿真模式导致 Agent 永久卡死**
- 证据：`main.cpp:186-195`——`activeProfileChanged`/`simulationModeChanged` 立即执行 `agent->setLLMService(...)` / `agentVM->setAgent(...)`；`AIAgent.cpp:81-92`——`setLLMService` 会 `disconnect` 旧 service 的全部信号。任务进行中切换时：in-flight 响应再无接收者，`m_active` 永真、状态永远 Thinking；仿真模式下 `setAgent(nullptr)` 同样不调 `agent->stop()`，`m_active=true` 残留，切回后 `startTask` 直接 return（`AIAgent.cpp:201`），无法再发消息。
- 建议：Batch 4——切换前若有活动任务先 `stop()`；`setLLMService`/`setAgent` 增加活动任务守卫。

**P2-6【新增】无重试/超时降级**：一次网络错误即 `failTask` 整个任务（`AIAgent.cpp:559-562`）；无瞬时错误重试、无可配置超时（硬编码 120s/300s，`OpenAIService.cpp:50`、`OllamaService.cpp:80`）。→ Batch 10。

**P2-7【新增】调试捕获文件残留隐私内容**：`.agent_capture/req_*.json` 保存了完整请求体（含知识库文档内容与 system prompt），且当前 `src/` 中已无写捕获的代码（grep 无结果），属于历史调试残留；未加入 `.gitignore`。→ Batch 12 前删除并 ignore；若需要捕获能力，须以显式开关 + 脱敏重建。

**P2-8【新增】可观测性缺失**：审计表只有 `session_id/event/tool/args/success/detail/timestamp`（`SqliteMemory.cpp:134-147`）；无 request_id/tool_call_id/latency/token usage/retrieval score/model 字段；日志为纯文本 qInfo。一次请求的完整链路（User→LLM→Tool→Retriever→Result→Final）无法按 ID 串起。→ Batch 11。

### P3（工程实现，随相关批次顺带修复）

### P4（性能/成本，Phase 8）

- 每次启动全量重新嵌入（`main.cpp:132-143`），无 chunk/向量持久化、无 content hash、无 embedding model version（`SqliteMemory.cpp:150-156` 仅存原文）。

## 7. 完整项目完善路线（Phase 0-10）

> 排序原则：**先防护网、后止血、再架构、后扩展**。与任务书给出的默认顺序相比有两处调整，理由如下：
> 1. **测试不是单独的 Phase 7，而是三段式**：Phase 0 建失败测试防护网（TDD 锁定 P0），各 Phase 自带验收测试，Phase 7 再做体系化补全（并发/矩阵/回归全集）。否则 P0 修复没有安全网。
> 2. **RAG 检索正确性（阈值/维度）提前并入 Phase 1**：改动小、体感直接（"知识库答非所问"），不值得等到 Phase 4；Phase 4 只做持久化与工程化。

### Phase 0 — 基线与测试防护网（Batch 0）
- **目标**：冻结基线（8/8 通过，已验证）；为 P0 问题补"修复前必失败"的回归测试。
- **任务**：Provider 连续请求状态测试（OpenAI/Anthropic `Tool→PlainText`）；`Knowledge→Normal→Knowledge` 行为矩阵测试（FakeService 驱动 Agent）；stop-then-new-request 测试。
- **风险**：低（纯测试）。**验收**：新测试全部按预期失败，旧 8/8 仍绿。

### Phase 1 — P0/P1 致命问题（Batch 1-3）
- **目标**：关闭确定性串扰、stale reply、封口、上限、RAG 正确性、恢复竞态。
- **依赖**：Phase 0 测试到位。**风险**：Batch 1 触及三 Provider 的请求路径（中高）；Batch 3 改检索语义需校准阈值（中）。
- **验收**：Phase 0 的失败测试全绿；12 章 v1 门槛清单 11 项全部达成（转为 Batch 3 出口条件，见第 8 节）。

### Phase 2 — Agent 生命周期与状态管理（Batch 4）

### Phase 3 — Tool Calling / 工具策略与安全（Batch 5）
- **目标**：工具数硬上限收尾、协作式取消、沙箱读策略、Prompt/Schema 收紧、passage 边界、隐私声明。
- **依赖**：Phase 2（请求上下文就绪）。**风险**：中（读策略收紧可能破坏现有用例，需提供设置开关）。
- **验收**：注入测试（恶意文档 → 不得自动读取白名单外文件）；行为矩阵知识库触发率符合预期。

### Phase 4 — Knowledge Base / RAG 工程化（Batch 6）

## 9. 推荐执行顺序

> **下一步：执行 Batch 0 → Batch 1。**

**为什么**：
1. 知识库串扰是当前唯一的确定性 P0，影响所有 Provider 的每一次会话，用户体感最差，且已定位到 3 行级别的最小修复（各 Provider 清理派生容器 + 基类请求令牌）。
2. Batch 0 的防护网成本极低（纯测试、无需网络），却能把"修复有效"变成可证明的事实，杜绝"缓解措施看起来生效"的回归（v1 的 44722fe 缓解正是前车之鉴）。
3. Batch 1 改动面小（4 个文件、每处数行），可独立验证、可单独回滚；完成即关闭 v1 门槛清单中最重的 4 项。
4. 在 Batch 1 落地前**不要**开展任何新功能（多工具、并发、更多 RAG 特性）——否则 P0 会从"知识库重复调用"扩散为通用 Agent 状态污染。

**后续节奏**：Batch 2/3 可并行（不同文件域）→ Batch 4（架构化，单独一个批次谨慎推进）→ 5/6 → 7/8 → 9/10/11 → 12。每个 Batch 结束跑全量 `ctest` 并更新本节勾选状态：

- [x] Batch 0 防护网（2026-09-05：`tests/test_provider_lifecycle.cpp` 8 用例 + `test_agent.cpp` 行为矩阵 3 用例；修复前 3 项确定性红、旧 8 套件保持绿，已实跑验证）
- [x] Batch 1 Provider 止血（2026-09-05：FIX-101 `resetStreamState()` 虚化+三 Provider 清理派生态；FIX-102 `m_requestGeneration` 请求令牌；FIX-103 尾行 flush；FIX-104 `choices=[]` 防御。`ctest` 9/9 绿、零警告、生命周期套件连续 6 轮稳定）

## 10. 总验收标准与执行纪律

### 10.1 最终完成定义（Done Definition）

| 维度 | 标准 |
|---|---|
| Functional | 普通对话、知识库问答、文件读写、shell 确认、流式、会话管理全部正常 |
| Architecture | 无已知 P0/P1；Provider 无跨请求状态；请求可标识、可取消、可封口 |
| Tool Calling | 工具仅在当前消息需要时调用；call_id 与 result 一一配对；执行数有硬上限 |
| Knowledge Base | `Knowledge→Normal` 不触发知识库工具（测试断言）；无关 query 返回 no-match；维度失配不返回噪声 |
| Isolation | 不同 session 状态不互串；stop/切换后新任务不受旧请求污染 |
| Testing | 全量 `ctest` 绿，覆盖 ≥90 用例；P0 回归永久保留 |
| Observability | 任一回答可凭 request_id 还原完整链路 |
| Security | 默认配置下模型无法自动读白名单外文件；注入文档无法诱导越权工具调用；隐私声明就位 |
| Documentation | README/架构文档与本计划结论一致；无过时表述 |

### 10.2 Agent 执行纪律（每个 Batch都必须遵守）

1. 修改前先读代码；不确定不猜测，用日志/测试取证。
2. 不为过测而改测试；不删功能绕问题；不做无理由重构；最小修改、不碰无关代码。
3. 每个 Batch 结束跑全量 `ctest`；发现新 P0/P1 立即记入第 3 节并重排 Batch。
4. 临时 workaround 必须在对应 Task 里标注"由 Batch X 收敛"，禁止无主 workaround。
5. 不伪造结果：未验证不得声称完成；验证命令与输出随 Batch 报告提交。
