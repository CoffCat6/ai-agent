## 1. 扩展面总览

NexusAI 有三个受支持的扩展面:

1. **新增工具**(Agent 能力):实现 `ITool` → 注册到 `ToolRegistry`;
2. **新增 LLM Provider**(接入新厂商):继承 `LLMServiceBase` 实现协议钩子 → 接入设置与装配;
3. **界面/ViewModel 扩展**:QML 单例注入模式 + QML 模块登记。

三者都不需要改动 `nexus_core` 的循环逻辑——这正是分层的意义。

## 2. 新增一个工具

### 2.1 契约

实现 `ITool`(`src/core/tools/ITool.h:45-50`)的两个纯虚函数:

```cpp
ToolDefinition definition() const override;                 // 名称/描述/JSON Schema 参数/安全级别
ToolResult execute(const QJsonObject& args) override;       // 执行体,返回 ok/fail
```

`ToolDefinition` 含 `name / description / parameters(JSON Schema)/ level`(:16-21);`ToolResult` 用 `ToolResult::ok()/fail()` 工厂构造(:24-35)。

### 2.2 执行环境约束(必读)

`execute` 在 **QtConcurrent 工作线程**上运行(`AIAgent.cpp:849-860`),因此:

- **禁止**触碰任何 GUI/QML 对象;需要 Qt 对象就自建(如 `QProcess`、`QFile`);
- 工具必须是**无状态、可重入**的(同类工具可能并发?不会——Agent 串行派发,但工具对象被注册表长期持有,不要把请求状态存在成员里);
- 网络等待要设超时(参考 `ShellExecTool` 的 1-60s 钳制,`ToolRegistry.cpp:198-199`);
- 返回前把超长输出截断(回灌给 LLM 的上限是 6000 字符,Agent 会再截一次;主动截断能让提示更友好,参考 `truncateOutput`,`ToolRegistry.cpp:35-39`)。

### 2.3 安全级别选型

| 你的工具行为 | 应选级别 |
|---|---|
| 只读、无副作用(读文件、列表、检索) | `Safe` —— 自动执行 |
| 修改状态(写文件、执行命令、发请求) | `RequiresConfirm` —— 每次弹窗等用户批准 |
| 明确危险(删除、格式化) | `Dangerous` —— 永不执行、永不暴露给模型 |

级别决定了循环行为(`AIAgent.cpp` 的 processNextToolCall 分支),也决定了 system prompt 的承诺("文件写入和命令需要用户批准")——**不要把写操作标成 Safe**。

文件/路径类工具**必须**走 `Sandbox::validatePath(path, isWrite)`(参考 `FileReadTool` 的做法,`ToolRegistry.cpp:62`);读操作受读白名单约束(默认 Documents/Downloads/Desktop/AppData,详见设计文档 §4.3)。

### 2.4 注册与接线

```cpp
// 方式 A:应用级动态注册(main.cpp,参考 KnowledgeSearchTool 的做法,main.cpp:114)
ToolRegistry::instance().registerTool(std::make_unique<MyTool>(/*依赖*/));

// 方式 B:作为内建工具(对所有启动方式生效)
// 在 ToolRegistry::registerBuiltins() 中追加一行(ToolRegistry.cpp:253-259)
```

带外部依赖的工具(如 KnowledgeSearchTool 依赖 RagService)用方式 A,在 main.cpp 组装点注册;纯独立工具用方式 B。

参数 schema 写法参考现成工具:`ToolRegistry.cpp` 顶部的 `stringParam/buildParams` 辅助,或 `KnowledgeSearchTool.h:82-94` 的私有版本。

### 2.5 审计与轨迹(自动)

不需要在工具内写任何日志/审计代码:

- 执行结果审计(成功/失败/参数摘要)由 Agent 在 `finishToolExecution` 自动落库(`AIAgent.cpp:878-881`);
- 轨迹节点(tool_call/tool_result)自动追加,参数与结果自动截断展示。

### 2.6 检查单

- [ ] `definition()` 的 description 写清楚"什么时候该用/不该用"(弱模型依赖它;参考 KnowledgeSearchTool 的写法,`KnowledgeSearchTool.h:19-26`)
- [ ] 级别正确;文件类工具过 Sandbox
- [ ] execute 无 GUI 依赖、有超时、输出截断
- [ ] 在 `tests/` 补测试(路径/沙箱类进 `test_sandbox.cpp`,Agent 行为矩阵进 `test_agent.cpp`)
- [ ] 若工具不应暴露给某些场景,考虑 `toolNamesForModel()` 的可见性语义(`ToolRegistry.h:24`)

## 3. 新增一个 LLM Provider

### 3.1 契约与继承

继承 `LLMServiceBase`(`src/infrastructure/llm/LLMServiceBase.h:49`),实现 8 个协议钩子(:65-84)。基类已经替你处理了最难的部分:

- 每请求上下文 `LLMRequestContext`(:27-41):requestId、行缓冲、累积内容、完成/错误标志;
- **回调身份校验**:陈旧/已取消 reply 的字节永远污染不了新请求(P0 修复的成果);
- finished 后的收尾阶梯:流式结果 → 非流 JSON → API error → 网络错误 → 空。

### 3.2 必须遵守的三条纪律

1. **请求状态只放 `ProviderRequestState` 子类**(:18-21),通过 `createRequestState()` 挂到上下文;**严禁**把响应累积状态存成服务对象成员——同一服务对象会被连续复用,成员状态会跨请求泄漏(这是本项目付出过 P0 代价的教训)。
2. **逐行处理**:`processLine(ctx, line)` 拿到的是去掉换行符的完整行;SSE 服务在这里自行剥 `data: ` 前缀,Ollama 类 NDJSON 直接解析。行拆分与半行缓冲由基类负责(`lineBuffer`,:31)。
3. **响应归属**:最终 `LLMResponse.requestId` 必须正确(基类回填);Agent 靠它丢弃被取代请求的迟到响应。

### 3.3 钩子实现指南

| 钩子 | 语义 |
|---|---|
| `createRequestState()` | 返回你的累积器(如 OpenAI 的按 index 分片工具调用累积) |
| `processLine()` | 解析一行:推进 content 流式增量(经基类发 `streamingChunk`)、累积 tool_calls、识别 done/错误事件 |
| `streamComplete()` | 累积状态是否已构成完整回答(如 Ollama 的 `done:true`) |
| `streamResult()` | 把累积状态装配成 `LLMResponse` |
| `providerLabel()` | 错误文案里的短名("API"/"Anthropic"/"Ollama") |
| `extractApiError()` | JSON 体里的错误负载;非错误体返回空 |
| `isCompleteBody()` / `parseBody()` | 非流式完整响应的判定与解析(**把解析器写成静态纯函数**,便于脱离网络测试) |

参考实现:同构 API 看 `OpenAIService`(SSE + 工具分片累积);异构 API 看 `OllamaService`(OpenAI wire format ↔ 厂商格式的双向转换——入参消息是 OpenAI 格式,你负责转换,`IAIService.h:20-24`)。

请求构建:直接用基类保护成员 `m_apiKey/m_model/m_baseUrl`,POST 经 `startReply(request, body)` 发起(:63),它会分配 requestId、发 `requestStarted` 并接线回调。记得给 request 设传输超时(参考 `OpenAIService.cpp:48`)。

### 3.4 接入设置与装配(四处改动)

1. **默认端点表**:`SettingsService.cpp:27-37` `providerDefaults()` 加一条(displayName/baseUrl/model/models);
2. **合法 provider 集合**:`SettingsService.cpp:39-41` `kKnownProviders`;
3. **装配点**:`main.cpp` `applySettings` 的 provider 分支(`main.cpp:207-249`,provider 选择在 :219-247)——实例化你的服务、加入 provider 选择逻辑;注意**只有活跃 provider 才接收 profile**;
4. **设置界面**:SettingsDialog 的 provider 选项加一项(QML)。

### 3.5 测试要求(项目惯例)

- **解析器纯函数** → `tests/test_llm_parsers.cpp`:正常/畸形/空/错误体/工具调用各来一遍,不碰网络;
- **生命周期** → `tests/test_provider_lifecycle.cpp`:用仓库里现成的 FakeSseServer 回环服务器走真实 `chatComplete`,钉死"工具状态跨请求清理"和"stale reply 不污染"两条 P0 行为。

## 4. ViewModel / QML 扩展模式

### 4.1 新增 QML 单例(带依赖注入)

1. 类声明:`QML_SINGLETON + QML_NAMED_ELEMENT(XxxVM)`,**构造函数带 parent 且不提供默认构造**——默认构造会让引擎绕过 `create()` 工厂,产出一个未注入依赖的第二实例(`AgentViewModel.h:90-94` 注释详述);
2. 静态 `instance()`(首次调用创建)+ `create(QQmlEngine*, QJSEngine*)`(直接返回 instance);
3. `CMakeLists.txt` 的 `qt_add_qml_module(nexus_viewmodels ...)` SOURCES 里登记(`CMakeLists.txt:85-98`);
4. `main.cpp` 在 `engine.load` **之前**取 `XxxVM::instance()` 并注入依赖(`main.cpp:121-133` 的顺序就是范式);
5. QML 里 `import NexusAI.ViewModels` 后直接用类型名。

### 4.2 新增 QML 组件/页面

- 新 `.qml` 文件加入 `qt_add_qml_module(nexus_ai ...)` 的 QML_FILES 清单(`CMakeLists.txt:117-141`);
- 面向用户的字符串一律包 `qsTr()`:lupdate 会汇入 `translations/nexus_ai_zh_CN.ts` 并随构建嵌入 `:/i18n`(FEAT-804,`CMakeLists.txt:159-167`),未翻译时回退源文;
- 颜色/字体一律取自 Theme 单例(如 `Theme.bgPrimary`、`Theme.brandPrimary`),不要硬编码色值——暗/亮主题依赖它;
- 与 C++ 交互遵循现有模式:QML 调 `AgentVM.xxx()` Q_INVOKABLE;C++ → QML 用信号(如 `toolConfirmRequired` → `ToolConfirmDialog`,`main.qml:237-245`)。

### 4.3 TraceModel 消费方注意事项

轨迹列表是增量模型:追加 → rowsInserted、节点更新 → dataChanged、会话切换 → modelReset。自定义 delegate 时不要依赖 `modelData`(参考 `AgentChatPage.qml:86-93` 的说明),展开/折叠状态要存在 view 层而非 delegate 层(会话切换的 modelReset 会重建 delegate)。

## 5. 对外接口规划(未来计划,未实现)

> **状态:设计未定,当前代码中不存在以下任何接口。** 本节仅作为后期演进的讨论基线,防止实现走样。

后期若要让第三方(脚本、其他桌面应用、局域网服务)复用 NexusAI 的 Agent/RAG 能力,候选方向:

1. **本地 HTTP 服务**(最可能):进程内起一个仅监听 127.0.0.1 的 REST/SSE 服务,暴露 `POST /sessions`、`POST /sessions/:id/messages`(SSE 流式回包)、`POST /knowledge/documents`。复用点:`AIAgent` 已经是信号驱动的,包一层 QHttpServer 即可;工具确认弹窗需要新的应答通道(等待用户批准 ↔ HTTP 请求挂起)。
2. **会话导入导出**:把 `messages + trace_nodes` 序列化为便携 JSON,这是所有对外开放的前置(可审计)。
3. **插件化工具**:从"编译期注册"演进为"运行期加载"(JSON manifest 描述 + 独立进程执行),安全模型需要先补齐进程级隔离——在 Sandbox 目前只管路径的情况下**不建议**做。
4. **MCP(Model Context Protocol)适配**:`ITool` 与 MCP tool 语义接近,可作为工具面的对外标准;Provider 面则相反,NexusAI 是客户端,无需暴露。

实现任何一条前,先补 `docs/5-完善计划.md` 中排定的重试/可观测性基建——对外接口会放大一切现有缺陷。
