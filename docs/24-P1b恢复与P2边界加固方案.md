## 2. P1b：D2 数据库恢复

### R1 `SqliteMemory::restoreFromBackup(const QString& backupPath)`

**待修复项**：恢复能力缺失（docs/23 D2 设计定稿，本项落地其文件与连接生命周期核心）。

**实际问题**：D1 只能备份与预览；损坏/误操作后没有把快照换回运行库的路径。换文件涉及"关连接 → 验证 → 保底 → 换文件 → 重开"五个必须原子的步骤，散落在调用方必然出错。

**修复后的改善**：一个方法完成全部恢复动作——任何一步失败都回到"原库原样 + 连接可用"，调用方只需处理布尔结果。

**如何修复**（`SqliteMemory` 新增，全部步骤在 GUI 线程调用方线程内同步执行）：

```cpp
// 调用前置条件：本实例之外，没有任何指向同一库文件的打开连接
//（UI 流程先 closeAllTabs；单实例锁 QLockFile 排除其他进程）。
bool SqliteMemory::restoreFromBackup(const QString& backupPath) {
    // 1. 关闭自身连接并注销（MEM-702 顺序：close → 置空 → removeDatabase）
    // 2. 校验备份：独立只读连接对 backupPath 跑 PRAGMA quick_check，
    //    非 ok 直接失败（原库未动）
    // 3. 保底：拷贝当前 <db> → <db>.pre-restore（回滚锚点）
    // 4. 备份 → <db>.restore-tmp 拷贝
    // 5. 删除现存 <db>-wal / <db>-shm（旧 WAL 混入新库文件会损坏）
    // 6. remove(<db>) + rename(<db>.restore-tmp → <db>)
    //    （QFile::rename 目标存在时失败，必须先 remove）
    // 7. 重走 open + PRAGMA(WAL/busy_timeout) + initDatabase()
    // 8. 成功：删除 .pre-restore，返回 true
    //    失败（7 重开失败或 6 后异常）：用 .pre-restore 覆盖回 <db> 再重开，
    //    返回 false；6 之前的失败：删除 tmp、直接重开原库
}
```

启动时发现残留 `<db>.pre-restore`（上次恢复中断）：保留不动并 `qWarning` 提示（不自动动库）。

### R2 `RagService::bumpRestoreGeneration()` + 恢复块提取

**待修复项**：`m_restoreGeneration` 只能被 `clear()/removeDocument()` 内部递增（`RagService.cpp:345、356`）；`main.cpp:541-583` 的知识库启动恢复块（RestoreItem 快照 + worker）不可复用。

**实际问题**：恢复流程要把"当前知识库状态"整体作废并从换库后的文件重新装载，需要外部触发生成号递增；恢复完成后需要重跑启动恢复块——现在没有入口。

**修复后的改善**：恢复编排可以两行完成知识库侧的作废与重载。

**如何修复**：

- `RagService` 新增 `void bumpRestoreGeneration()`——锁内 `++m_restoreGeneration`（在途恢复步骤按既有 generation 校验自行作废；`ingestRestoredDocument` 的嵌入会白做一段，但函数返回 -2 前不会 emit 任何信号，不污染换库后的库）。
- `main.cpp` 把恢复块提取为匿名命名空间函数 `startKnowledgeRestore(SqliteMemory* memory, RagService* rag)`（RestoreItem 结构、快照、`(void)QtConcurrent::run` worker 原样搬入）；启动路径与 R4 恢复完成后各调用一次。签名与行为零变化，纯提取。

### R3 `AgentViewModel::closeAllTabs()` + 同步析构冲刷

**待修复项**：`closeTab(int)` 拒绝关闭最后一个标签（`m_tabs.size() <= 1` 保护，AgentViewModel.cpp），且用 `deleteLater`——per-tab 的 SqliteMemory 连接要等事件循环才真正关闭。

**实际问题**：换库文件时只要有任何 per-tab 连接未关，Windows 上 rename 会因文件被占用而失败；即使成功，悬挂的旧连接也构成未定义行为。"关掉全部标签"必须是恢复编排可以同步依赖的前置条件。

**修复后的改善**：一个内部方法保证返回时**零个 per-tab 连接存活**。

**如何修复**：

```cpp
// AgentViewModel 内部（非 Q_INVOKABLE）：绕过末标签保护。
void AgentViewModel::closeAllTabs() {
    for (ChatSessionController* c : std::as_const(m_tabs)) {
        c->stop();               // 封口未答工具调用（既有 stop 语义）
        c->deleteLater();
    }
    m_tabs.clear();
    m_activeTab = -1;
    // 上述信号批量补发（复用 closeTab 的信号清单）
    ...emit...
    refreshSessions();
}
```

R4 编排在调用它之后、动文件之前执行**同步冲刷**，把 deleteLater 立即兑现（F2 后 per-tab 连接在 controller 析构链中随 agent 销毁关闭）：

```cpp
QCoreApplication::sendPostedEvents(nullptr, QEvent::DeferredDelete);
```

QML 侧不持有 controller 对象引用（tabModel 是 QVariantMap 值拷贝），同步析构安全；恢复完成后立即 `openTab()` 回到单标签常态。

### R4 `restoreDatabaseFrom()` 编排 + 恢复入口

**待修复项**：设置与备份页只能预览，不能执行恢复。

**如何修复**：

```cpp
// AgentViewModel，GUI 线程同步执行（用户显式动作，数秒级阻塞可接受）：
QString AgentViewModel::restoreDatabaseFrom(const QString& path) {
    // 0. 预检：inspectBackupFile(path) 的 integrityOk 必须为 true
    // 1. closeAllTabs() + sendPostedEvents(DeferredDelete) 冲刷
    // 2. rag->bumpRestoreGeneration()（作废在途恢复 worker）
    // 3. const bool ok = memory->restoreFromBackup(path)
    //    —— memory 即 m_memory（进程级实例），usageMemory/Activity sink/
    //       modelConfigurator 捕获的裸指针经 reopen 后全部继续有效
    // 4. startKnowledgeRestore(memory, rag)（R2 提取的函数，重新装载知识库）
    // 5. openTab()（回到单标签）+ Activity 记账
    // 返回：空串 = 成功；否则用户可读错误（"备份损坏"/"恢复失败已回滚"）
}
```

设置与备份页：D1 预览卡片追加「从此备份恢复」按钮（仅 integrityOk 时可用）→ 确认对话框（复用预览数据 + docs/23 §9.1 文案：恢复会关闭全部标签并停止在跑任务）→ 调用后按结果设置 statusMessage。全程持有单实例锁，无双写窗口。

### R5 失败注入专项验收（docs/23 §9.3 落地）

`tests/test_memory.cpp` 新增（SqliteMemory 层，编排层逻辑由 test_viewmodel 的既有标签夹具冒烟覆盖）：

1. **成功路径**：库 A（含 2 会话）备份 → 库 B（含 3 会话）→ `restoreFromBackup(快照A)` → 断言 B 文件的行数等于 A、`user_version == 1`、`.pre-restore` 已清理、连接可用（写入新消息成功）。
2. **损坏备份**：对非 SQLite 文件执行恢复 → 返回 false，原库行数不变、连接仍可读写。
3. **回滚路径**：用"合法 SQLite 但缺表"的伪备份（手工建空库）触发重开后 initDatabase 之外的一致性差异——断言返回 false 且原库数据完整（`.pre-restore` 回滚生效）。
4. **换库后知识库自愈**：restorePersistedDocument 对换库后不存在的文档在重载时按普通恢复路径处理（test_rag 既有用例覆盖，不新增）。

## 3. P2：边界加固十项

### H1 `HttpTransport` 响应缓冲上限（中）

**问题**：`HttpTransport.cpp:104-109` 的 JSON 累积路径与 SSE 帧缓冲均无上限，恶意/异常服务器可在超时窗口内喂爆内存。

**改善**：单回复缓冲超过 **32 MiB** 即判协议违规——置错误并中止 reply（fail closed），连接进入既有 errorOccurred 链路。

**修复**：`onReadyRead` 追加前检查 `buffer.size() + chunk.size() > kMaxResponseBytes`（常量 32 MiB，与 `http_fetch` 的 1MB 语义区分：MCP 响应体含工具结果，上限放宽但必须有界）；超限走 `emit errorOccurred(...)` + `reply->abort()` + 清理 `m_sseBuffers[reply]`。**回归**（test_mcp）：脚本 HTTP 假服务器发送超限体 → 断言 transport 报错且无崩溃。

### H2 `StdioTransport` stdout 行缓冲上限（中）

**问题**：`StdioTransport.cpp:175-183` 的 `m_lineBuffer` 只在遇到 `\n` 时消费；服务器输出无换行字节流时无界增长（stderr 已有 64KB 尾部保留，stdout 没有）。

**改善**：行缓冲超过 **8 MiB** 视为协议违规——记录诊断、杀掉服务器进程树（复用 stop() 路径），连接进入重连退避。

**修复**：`onReadyRead` 追加后检查 `m_lineBuffer.size() > kMaxLineBufferBytes` 且不含 `\n` → `qWarning` + `m_process.kill()`（onFinished 收尾清缓冲）。**回归**（test_mcp）：假服务器输出 8MB+ 无换行 → 断言进程被终止、错误可见。

### H3 `read_file` 预读上限（中）

**问题**：`ToolRegistry.cpp:86` `readAll()` 无预读上限——20k 字符的输出截断发生在**全量载入内存之后**，且该工具是免确认的 Safe 级；提示注入后的模型可指向超大文件制造内存尖峰。

**改善**：超限文件在打开后、读取前拒绝。

**修复**：`file.open` 后 `if (file.size() > kMaxReadFileBytes) return fail(...)`（常量 8 MiB——源码/文本文件远小于此，二进制本就不是目标物）。**回归**（test_sandbox）：生成 9MB 文本文件 → `read_file` 失败且错误含大小说明；普通文件不受影响。

### H4 `EpisodicService` 请求配对与挂起泄漏（中）

**问题**：`EpisodicService.cpp:61` 的 `requestId = m_pendingSummaries.size() + 1` 非单调（删一条后 size 回退、key 碰撞覆盖）；`:64-67` one-shot 连接不校验 `response.requestId`，`onSummaryResponse` 按 FIFO 取首个 pending——同 tab 并发两个摘要时响应串会话；请求被 `LLMServiceBase` 顶掉时不发任何信号，pending 条目与 one-shot 连接永久悬挂（无超时兜底）。

**改善**：摘要与响应严格配对；悬挂请求 90 秒超时清理。

**修复**：成员 `quint64 m_nextSummaryRequestId{1}` 单调递增；`connect(m_llmService, &IAIService::responseReady, this, [this, conn, requestId](const LLMResponse& r) { disconnect(*conn); onSummaryResponse(requestId, r); })`——lambda 捕获自己的 requestId，路由不再依赖 FIFO；`onSummaryResponse(requestId, response)` 按 key 取 pending，找不到即丢弃（陈旧响应）；`QTimer::singleShot(90s, ...)` 超时则断开连接并移除 pending（90s > LLM 请求既有超时）。**回归**（test_episodic）：录制服务返回带 requestId 的响应——错序响应被丢弃、正确路由；被顶掉的请求超时后 pending 清空。

### H5 `OllamaEmbedding` 批次重试（低）

**问题**：`embedBatch` 任一批瞬时失败（Ollama 重启/超时）→ 直接返回 `{}` → 整篇文档永久降级伪嵌入，只能手动重嵌。

**改善**：每批一次自动重试；仍失败才整体降级（契约不变）。

**修复**：批内 POST 包一层 `for (int attempt = 0; attempt < 2; ++attempt)`，失败后 `QThread::msleep(500 * (attempt + 1))` 重试一次；**仅对网络/超时错误重试**，数量不匹配与空向量不重试（是协议错误，重试无意义）。**回归**（test_embedding）：假服务器第一次返回 500、第二次成功 → 断言批次完成且 progress 计数正确。

### H6 退出期 rag worker 守护（中）

**问题**：三处 `(void)QtConcurrent::run` 捕获裸指针 `rag/ragPtr` 且丢弃 QFuture——`main.cpp:569`（启动恢复）、`main.cpp:694`（全量重嵌）、`AgentViewModel.cpp:938`（导入）。用户在后台任务进行中退出时，`rag`（parent 到 app）先于池线程任务销毁 → use-after-free。

**改善**：worker 与 rag 的生命周期解耦，退出竞态从根上消除。

**修复**：`RagService` 改为**有意的过程生命周期对象**——`new RagService(nullptr)`（不再 parent 到 app，永不 delete，注释声明"池线程可能持有其指针运行至进程退出，与 memory（main.cpp:235）同一纪律"）。三处捕获零改动；QObject 信号（documentPersisted 等跨线程 emit）的消费者连接本就以 `&app` 为上下文排队（main.cpp:446-457），无 parent 不影响投递。**回归**：既有全量 ctest（行为零变化，纯生命周期声明）。

### H7 `shell_exec` 敏感环境变量剔除（中）

**问题**：`ToolRegistry.cpp:334` 子进程继承父进程全部环境变量——模型可借 `set` 把 `OPENAI_API_KEY` 等读进工具输出 → 上下文 → 可能外发。

**改善**：敏感变量在执行前剥离，正常工具用途不受影响。

**修复**：构造 `QProcessEnvironment` 时过滤——键名包含 `API_KEY` / `APIKEY` / `TOKEN` / `SECRET` / `PASSWORD`（大小写不敏感）的条目剔除，白名单例外 `PATH`/`SYSTEMROOT` 等系统必需项不受影响（它们不含敏感词）。**回归**（test_sandbox）：设置一个 `TEST_API_KEY=secret` 环境变量 → `shell_exec` 执行 `set TEST_API_KEY`（Windows）/`env`（POSIX）→ 断言输出不含该值。

### H8 Sandbox 静态策略变量跨线程同步（低）

**问题**：`Sandbox.h:310-315` 的 `s_readPolicy/s_projectDir/s_projectWrite/s_userDenyList` 是 GUI 线程写、池线程读的裸 inline static（同文件 `s_execProjectDir` 用 QThreadStorage 是正确写法，这四个遗漏）——标准数据竞争（UB）。

**改善**：策略读写有同步保证；热路径开销一次读锁。

**修复**：新增 `inline static QReadWriteLock s_policyLock`；四个 setter（`setReadPolicy/setProjectDir/setProjectWriteEnabled/setUserDenyList`）写锁；`validatePath`/`resolvePath`/`currentProjectDir`/`isDenied`/`readPolicy`/`projectWriteEnabled` 读锁（`validatePath` 在入口取一次读锁覆盖整次判定最简单——注意 `ExecutionScope` 的 QThreadStorage 槽不加锁，纯线程局部）。**回归**：既有 test_sandbox 全量（行为零变化）；并发场景由工具执行路径天然覆盖。

### H9 MCP client 退役延迟删除（低）

**问题**：F1（docs/22）后 adapter 靠 dispatch 的 shared_ptr 存活，但 `McpManager` 移除路径仍立即 `deleteLater` client——adapter 池线程 `invokeMethod(client,...)` 与 client 析构**同时发生**的瞬间仍有理论窗口（docs/22 §9 登记）。

**改善**：client 比"可能仍在跑的 execute 上限"活得久，窗口归零。

**修复**：`McpManager` 三处移除点（removeServer/setEnabled(false)/applyRestoredConfigs）把 `client->deleteLater()` 替换为延迟退役：

```cpp
// docs/24 H9: 比在跑 execute 的上限（35s）+ 取消宽限（3s）更久才析构，
// 池线程上的 invokeMethod(client, ...) 从此必然命中存活对象。
QTimer::singleShot(40s, client, [client]() { client->deleteLater(); });
```

client 与 manager 断连后闲置 40 秒（不接新请求），届时统一销毁。**回归**（test_mcp）：移除服务器后立刻断言 registry 无该工具 + client 仍在（QPointer 探针），40s 行为不进单测（时延型，靠实现评审）。

### H10 旧版明文 apiKey 注册表残留清理（低）

**问题**：`migrateLegacy`（`SettingsService.cpp:423`）把旧版顶层 `apiKey` 迁进 profile（重新 DPAPI 加密）后**不删除原键**——注册表明文残留（docs/22 审查确认）。

**改善**：迁移完成后顶层明文键从注册表消失。

**修复**：`migrateLegacy` 成功产出 profile 后 `SettingsRepository::remove(QStringLiteral("apiKey"))`（连同已迁空的顶层 `provider` 键一并清理；scoped `<provider>/baseUrl|model` 键保留——它们非敏感且 `contains()` 探测仍在用）。**回归**（test_settings）：写入顶层明文 `apiKey` → 触发迁移 → 断言注册表键已不存在且 profile 内密钥经 DPAPI 可解。
